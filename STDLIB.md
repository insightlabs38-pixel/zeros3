# STDLIB Log

What ZeroS3 actually ships is one file, `zeros3.go`, built entirely on
the Go 1.27 standard library. This log maps every role a project like
this would normally reach for a third-party package to the exact stdlib
facility ZeroS3 uses instead, and what ZeroS3 had to build itself to fill
the gap. Every line below points at real, shipped code — nothing here is
aspirational.

## 1. Environment

- **Go version:** `go1.27.0` (see `go.mod`'s `go 1.27.0` directive; the
  toolchain is resolved automatically by `GOTOOLCHAIN=auto`, or can be
  installed explicitly from `go.dev/dl`).
- **CGO:** `CGO_ENABLED=0` — no cgo, no C toolchain, no dynamic linking
  requirement. Verified by the release build (`scripts/reproducible_build.sh`).
- **Platform:** Linux amd64 is the release-blocking, fully crash/
  concurrency-tested target. The build itself is not Linux-specific
  (nothing platform-specific is imported), but only Linux amd64 carries
  the durability/crash-recovery test coverage this project's claims rest
  on.

## 2. Dependency proof summary

- `go.mod` has **no `require` block** — see `go.mod` itself.
- No `go.sum` file (nothing to lock).
- No `vendor/` directory.
- No `golang.org/x/...` import in `zeros3.go` (Go's own standard-library
  packages such as `net/http` and `crypto/tls` vendor `x/net`/`x/text`/
  `x/crypto` *inside the toolchain itself* — that's part of every Go
  program ever built with `net/http`, not a ZeroS3 dependency; see
  `deps-proof.txt`).
- No subprocess/shell-out: `zeros3.go` never imports `os/exec` and never
  invokes an external binary at runtime.
- Full evidence, generated by `go list -deps .` and `CGO_ENABLED=0 go
  build`, lives in `deps-proof.txt` at the repository root.

## 3. Core substitutions table

| # | Role a normal project would reach for | Go 1.27 stdlib used instead | What ZeroS3 had to build | Tradeoff |
|---:|---|---|---|---|
| 1 | HTTP server/router (Express/Koa-style, or a Go router like `chi`) | `net/http` (raw `http.Handler`, no `http.ServeMux`) | S3 method/subresource dispatch by hand, deliberately *without* path normalization (`splitRawRequestURI`, `handleRequest`) | `ServeMux` cleans `//`, `.`, `..` — exactly the bytes SigV4 must sign unmodified. | 2 | AWS SigV4 signer/verifier (e.g. `aws/signer/v4`) | `crypto/hmac`, `crypto/sha256`, `crypto/subtle`, `encoding/hex`, `net` (`net.SplitHostPort` for virtual-host `Host` parsing) | Full Authorization-header *and* query-string (presigned-URL) SigV4, sharing one canonicalization/signing core (`sigv4VerifyCore`, section 8); `zeros3 presign`'s URL generator calls the identical primitives | The entire canonicalization algorithm (raw-path preservation, query sorting, header canonicalization) is authored logic; the primitives are stdlib, the protocol is not. |
| 3 | Content-defined chunking library (e.g. `restic/chunker`) | Hand-rolled Gear hash over `[]byte`, table seeded via `crypto/sha256` | Streaming CDC chunker with FastCDC-style min/target/max normalization (section 3) | No stdlib CDC exists; this is fully authored, stdlib only supplies the hash used to derive the deterministic gear table. |
| 4 | UUID library (e.g. `google/uuid`) | Go 1.27 stdlib `uuid` package (`uuid.NewV7`) | Nothing — this is a genuine "package killed": manifest/version/store IDs use the stdlib generator directly | None; this is the cleanest substitution in the project. |
| 5 | Embedded metadata DB (e.g. `bbolt`) for tracking what exists | `os`, `io`, `hash/crc32` | An append-only, CRC32C-framed, replay-based "visibility journal" (section 6) that is the sole source of truth for the bucket/object namespace | A real engineering tradeoff: no transactions/indexes/queries for free — replay-on-open and an in-memory map are hand-built. |
| 6 | XML codec (e.g. `fast-xml-parser`) | `encoding/xml` | S3 response/error XML shapes (`listBucketResult`, `copyObjectResult`, S3 error envelope) | Stdlib's `encoding/xml` handles escaping/marshaling directly; no gap to fill. |
| 7 | JSON codec/CLI reporting library | `encoding/json` | Manifest/`FORMAT.json`/journal-payload encoding, `stats -json`/`verify -json` output | None; stdlib JSON is a complete fit. |
| 8 | CLI framework (e.g. Cobra, `commander`) | `flag`, `os.Args` | Subcommand dispatch (`serve` default, `stats`, `verify`, `presign`, and — M5-C — `versions`, `restore`, `gc`, `doctor`), usage/exit-status contract (section 16/17) | `flag` has no subcommand concept built in; ZeroS3 dispatches on `os.Args[1]` itself and gives each subcommand its own `flag.FlagSet`. |
| 9 | Checksum/integrity library | `hash/crc32` (with the Castagnoli table), `encoding/base64` | Ordinary `x-amz-checksum-crc32` request validation, journal frame CRC32C | Both uses share `hash/crc32`; nothing third-party was ever needed here. |
| 10 | S3-compatible single-part ETag (MD5-based) | `crypto/md5` | `buildManifestV1`'s ETag computation | MD5 here is explicitly *not* a security use — it exists solely to match S3's documented single-part ETag convention (`//nolint:gosec` marks this deliberately). |
| 11 | Advisory file locking (e.g. `gofrs/flock`) | `syscall` (`syscall.Flock`, `LOCK_EX`/`LOCK_SH`/`LOCK_NB`/`LOCK_UN`) | Exclusive-ownership enforcement for `zeros3 gc` (section 13b): a shared lock for an ordinary store user (`zeros3 serve`), an exclusive, non-blocking lock GC must win before it may delete anything | `syscall.Flock` is Unix-specific (fine: Linux amd64 is the sole release-blocking platform per section 1 above); no third-party lock library was needed. |
| 12 | Bounded worker pool / errgroup (e.g. `golang.org/x/sync/errgroup`, `golang.org/x/sync/semaphore`, or a third-party pool library) | `context`, `sync` (`sync.WaitGroup`), a plain buffered channel as a counting semaphore | `runTransferWorkers` (M8H-B): bounded-concurrency chunk transfer for `replicate`/`repair`/`sync` | `errgroup` is itself `golang.org/x/...` (explicitly out of scope, see section 2) — its whole job here is one `WaitGroup` plus one buffered-channel semaphore, small enough that authoring it directly was simpler than working around the `x/sync` restriction. |
| 13 | Graceful-shutdown/signal-handling library (e.g. `tableflip`, `overseer`) | `os/signal` (`signal.Notify`/`signal.Stop`), `context.WithTimeout`, `net/http`'s own `http.Server.Shutdown` | P1-B's SIGINT/SIGTERM handling in `runServe`: bounded-grace drain, second-signal-forces-exit | `signal.Notify` and `http.Server.Shutdown` already do essentially everything needed; the only authored logic is the small `select` deciding first-signal-vs-second-signal-vs-serve-error. |
| 14 | TLS termination (e.g. a reverse-proxy sidecar, or a cert-automation library like `autocert`'s ACME client) | `net/http`'s `http.Server.ListenAndServeTLS`, `crypto/tls` (used only internally by that call) | P1-C's `-tls-cert`/`-tls-key` flags on `runServe` | Deliberately the smallest possible integration: no ACME, no cert generation/renewal/mTLS/custom `tls.Config` — an operator supplies a cert/key pair or gets plain HTTP, nothing in between was built. |

## 4. Storage substitutions

- **Filesystem primitives:** `os`, `io`, `io/fs`, `path/filepath` for the
  store's directory layout (`chunks/`, `manifests/`, `journal/`, `tmp/`),
  durable file publication (`writeFileDurable`: stage in `tmp/`, fsync,
  rename into place), and directory fsync (`syncDir`) — the only
  portable way to make a rename durable on Linux.
- **Content-addressed storage identity:** `crypto/sha256`, `encoding/hex`
  for chunk/manifest naming and re-verification on every read
  (`casWrite`/`casRead`).
- **Buffered/streaming IO:** `bufio`, `io.Reader`/`io.Writer` for the CDC
  chunker (`cdcChunker`, bounded to `cdcMaxChunkSize` bytes of memory
  regardless of object size) and deep verify's per-chunk streaming
  SHA-256 pass (never buffers a whole reconstructed object).
- **Synchronization:** `sync.Mutex` — `Store.mu` as the single writer
  lock for the visible namespace, `Journal.mu` guarding the append
  cursor and poison state. No worker-pool/channel machinery was needed;
  the concurrency model is deliberately a single conservative lock, not
  a scheduler.

## 5. Protocol substitutions

- **Router:** see table row 1.
- **SigV4:** see table row 2.
- **Checksum/client-integrity behavior:** see table row 9; also
  `encoding/base64` for the checksum header's base64 encoding and
  `net/url` for percent-decoding request paths and (leniently)
  `x-amz-copy-source`.
- **HTTP client-facing types:** `net/http` status codes and header
  manipulation for the S3-shaped GET/HEAD/PUT/DELETE/Range responses;
  `strconv` for the numeric header fields (`Content-Length`,
  `Content-Range`).
- **HTTP client library (M6, `zeros3 sync`):** `net/http`'s `http.Client`/
  `http.NewRequest`, used as a genuine outbound HTTP *client* for the
  first time in this codebase — every other CLI verb (`stats`/`verify`/
  `versions`/`restore`/`gc`/`doctor`) operates directly on a `-store DIR`,
  never over the network. No third-party HTTP client (`resty`,
  `req`, etc.) was needed; `signSigV4Request` (section 15b) reuses the
  server's own SigV4 canonicalization primitives (`sigv4CanonicalURI`/
  `sigv4CanonicalQuery`/`sigv4CanonicalHeaders`/`sigv4SigningKey`) rather
  than a second signing implementation.
- **ZeroS3 sync extension wire format (M6):** `encoding/json` for the
  `/_zeros3/v1/...` request/response bodies — the same package already
  used for manifests/`FORMAT.json`/journal payloads/`-json` CLI output
  (table row 7), applied here to a genuinely new role (an HTTP
  request/response wire format, not just on-disk/CLI encoding).
- **Remote-to-remote delta replication (M8A, `zeros3 replicate`):**
  `net/url`'s `url.Values` for encoding the object-descriptor endpoint's
  `bucket`/`key` query parameters — a genuinely new role for a package
  already in use (row 5's `x-amz-copy-source` percent-decoding): letting
  `net/url` build the query string sidesteps the exact raw-path-
  concatenation bug class the M7 hostile review found and fixed in
  `zeros3 sync`'s own client (a `%`/`#`/`?` in a *path segment* needs
  hand-rolled escaping; the same bytes in a *query value* are simply
  `url.Values.Encode()`'s job). No new HTTP client, signer, or JSON
  library was needed — `replicateObject` (section 15d) reuses
  `signAndDo`/`discoverZeroS3Sync`/`negotiateSyncMissing`/`putSyncChunk`/
  `commitSyncObject` unmodified.
- **Recursive directory traversal (M6C, `zeros3 sync LOCAL_DIRECTORY ...`):**
  `path/filepath`'s `WalkDir`, used here for the first time in this
  codebase to walk a client-side source tree rather than a single named
  path. Its documented behavior — each directory's entries are read once
  and sorted by name before descending — is exactly the deterministic,
  lexically-stable traversal order C1 requires, so no separate sort step
  was needed; `fs.DirEntry.Type()` (from the same `readdir`-derived entry,
  never a followed `Stat`) is what lets a symlink be identified and
  skipped without ever being dereferenced. No third-party directory-walk
  or glob library was needed.

- **Peer-assisted repair (M8B, `zeros3 repair`):** `io.LimitReader`, used
  here for the first time in a genuinely new role: bounding an *outbound
  HTTP client's own response* read (`fetchRepairChunk`), rather than its
  existing role of bounding an *inbound server request* body (row 1's
  `maxRequestBodySize` check). No new package was needed for this --
  repair's one new security requirement (never let a peer force an
  unbounded read into memory) is exactly what the same primitive already
  does, applied the other direction. Every other piece --
  `signSigV4Request`, the `/_zeros3/v1/chunks/<sha256-hex>` endpoint,
  `discoverZeroS3Sync`, `writeFileDurable`/`syncDir` -- is unmodified M6/
  M8A code; no new stdlib package was needed for detection
  (`computeReachability`, already `encoding/json`+`crypto/sha256`-based)
  or publication (already `os`+`path/filepath`-based).

- **Prefix/bucket delta replication (M8C, `zeros3 replicate -recursive`):**
  no new stdlib package at all — `go list -deps .`'s package list is
  byte-for-byte identical to the M8B-recorded proof. The one genuinely
  new *role* is `encoding/xml`'s `xml.Unmarshal` (`listSourceObjects`)
  decoding an outgoing HTTP *client* response — the server already uses
  `encoding/xml` twice (`xml.NewEncoder` to write `ListObjectsV2`'s own
  XML response, table row 9's `handleCompleteMultipartUpload`'s
  `xml.Unmarshal` to read an *inbound request* body) but M8C is the first
  place this codebase parses XML it received *as a client of another
  ZeroS3 server*, reusing the exact same `listBucketResult`/`xmlContent`
  types the server already declares to encode that same shape. Every
  other piece — `signAndDo`, `url.Values`/`url.URL.EscapedPath()` for the
  listing request, `replicateObject` itself — is unmodified M6/M8A code.

## 6. Developer-tool substitutions

- **CLI:** see table row 8.
- **Logging:** `log` — request/error diagnostics to stderr; stdout is
  reserved for command output (`stats`/`verify` results), matching the
  CLI's stdout=data / stderr=diagnostics contract.
- **Testing:** Go's own `testing` package, plus `net/http/httptest` for
  full HTTP-handler round trips and `httptest.NewServer` for real-socket
  tests. No third-party test framework (`testify`, `ginkgo`, etc.) is
  used anywhere in `zeros3_test.go`.
- **UUID:** see table row 4.

## 7. External test-only software (never a runtime dependency)

The [`zeros3-testing`](https://github.com/insightlabs38-pixel/zeros3-testing)
repository pins the AWS SDK for Go v2
(`github.com/aws/aws-sdk-go-v2/...`) purely as a black-box S3 client to
exercise ZeroS3's wire protocol from the outside. It is a separate Go
module, in a separate repository, that talks to a `zeros3` binary only
over HTTP — never imported by, linked into, or required by the `zeros3`
module. See that repository's own `README.md` for its pinned versions
and harness list.

## 8. What the stdlib did not provide

None of the following exist in the Go standard library; they are fully
authored logic in `zeros3.go`:

- S3's request/response semantics (bucket/object model, `ListObjectsV2`
  pagination/continuation-token contract, error code/XML shapes,
  metadata-directive rules for `CopyObject`).
- SigV4 request canonicalization (the raw-path-preservation rule, query
  encode-then-sort, credential scope validation) — stdlib supplies HMAC/
  SHA-256/hex, not the algorithm.
- Content-defined chunking (Gear-hash boundary selection, FastCDC-style
  normalization, the deterministic gear table).
- A durable storage engine: the CAS layout, immutable-manifest model,
  and append-only checksummed visibility journal, including its replay/
  recovery/poisoning semantics.
- The `stats`/`verify` model: exact-scan dedup accounting (logical vs.
  unique vs. exclusive vs. shared bytes) and the multi-layer integrity
  check `verify` performs (structural → per-chunk → whole-object digest).
- **M5-C:** internal (non-AWS-API) immutable object version history and
  zero-copy restore; the one authoritative CAS/manifest reachability scan
  (`computeReachability`, section 12a) that unifies current objects,
  retained historical versions, and active multipart uploads into a
  single live-root/live-chunk model consumed by stats, verify/doctor, and
  GC alike; and offline, exclusive, dry-run-by-default GC built on top of
  it.

## 9. Tradeoffs / limits

- **No connection pooling/multiplexing tuning beyond `net/http`'s
  defaults** — a production S3-compatible service would likely tune
  `http.Server`/`http.Transport` more aggressively; ZeroS3's scope is a
  local/self-hosted development store, not a high-throughput production
  target.
- **No structured logging library** (`log/slog` was considered but
  plain `log` was sufficient for this project's actual diagnostic
  needs — this is a deliberate "didn't need it," not a gap).
- **No retry/backoff library** — `zeros3 sync`'s client (M6) makes one
  attempt per request and reports failure rather than retrying; a local
  file mutated mid-operation aborts, and resuming after an interrupted
  transfer or server restart falls out of CAS's own content-addressed
  durability (re-running `sync` naturally re-negotiates only the chunks
  still missing) rather than any bespoke retry/session state. `zeros3
  replicate` (M8A) inherits exactly the same story: no replication-
  session database anywhere, so an interrupted or killed `replicate`
  process is simply re-run, and CAS makes the resume correct on its own.
  `zeros3 replicate -recursive` (M8C) inherits it a second time, one
  level up: no namespace-replication session database either, so an
  interrupted or killed namespace run is simply re-run — its fresh
  enumeration plus each object's own M8A resume behavior make it correct.
- **No online/concurrent GC** — `zeros3 gc` requires exclusive ownership
  of the store (via `syscall.Flock`, row 11 above) and refuses to run
  while `zeros3 serve` (or another `gc`) holds it; a scheduler for
  background/concurrent garbage collection was explicitly out of this
  milestone's scope, so nothing needed one.
- **A real embedded database** (e.g. `bbolt`) would give ZeroS3
  transactions, indexes, and range queries for free; the hand-rolled
  journal-replay model trades that convenience for zero dependencies and
  full control over the exact durability contract documented in
  `STATUS.md`.
