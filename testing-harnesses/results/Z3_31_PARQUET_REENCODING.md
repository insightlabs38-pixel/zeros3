# Z3-31 — Exact Parquet page/value re-encoding frontier
Laboratory only; `zeros3.go`, its tests, root `go.mod/go.sum`, ZS3R/ZS3T, Store format 6 and production kinds are untouched (diff empty). Code: `z3/thriftcompactz3`, `z3/parquetz3`, `z3/snappyz3` (+fragment predictors), `z3/repz3/kinds/parquet.go` (lab `KindParquet` = 10), `z3/cmd/z3parquet`, producers `z3/oracle/parquet`. Starting `main` 7262f4e.
**Question.** Can column values be stored once as content-addressed logical streams plus a bounded exact page/compression recipe, so row-group, page, dictionary, codec and producer rewrites reuse them and the original bytes still rebuild exactly? **Yes for flat PLAIN/RLE/dictionary/byte-stream-split pages under Snappy, Zstd or no compression; everything else falls back to opaque payloads or CDC.**
**Decisions.** Parquet logical representation `PROMOTE_TO_I3` (flat subset) · Compact Thrift parser `CORE_PORTABLE` · page layout predictors `CORE_PORTABLE` · Snappy replay `CORE_PORTABLE` · Zstd replay `PORT_SMALL_REFACTOR` · `KindParquet` **YES**. Strongest: 8-revision history 89.7 → 28.9 MiB (3.1×), row-group resize 19.3 MiB → 17.6 KiB, delete-in-middle 14.9 MiB → 146 KiB. Strongest negatives: 4 KiB reads pay a whole page (101× vs CDC 18×), DELTA_*/nested/GZIP/LZ4 are not logical, and first-sight savings (−22 %) are mostly standalone recompression, not dedup.

## 2. Architecture (all exactness comes from bytes, never from a Parquet library)
Parse (`io.ReaderAt`, bounded footer/Thrift/pages, exact span tiling) → per page: decompress, decode levels+values, re-encode, compare bytes (**evidence 1**) → recompress, compare payload (**2**) → whole-file Decode from recipe+components, length/SHA-256/bytes (**3**). Per column two streams: canonical values (PLAIN form; dictionary IDs are never identity) and null runs; cut by a content-defined gear hash over record bytes (min T/4, max 4T, T = 8 KiB), digest nodes (avg 64 groups) so one changed group is one node. Recipe = raw page headers + footer inline, per-page flags (compression id, layout mode, non-null count), roots; leaf groups hang off nodes (VIA). A page with an unverifiable layout makes its chunk opaque (payloads kept); a file with no logical chunk, an unknown codec only, or a broken footer returns `ErrUnsupported` → CDC. Z3-30's `HashCutter` was not reusable (it hashes a user key; a value-only hash degenerates on low-cardinality columns), the pattern was.

## 9. Limitations and carry-forward
Two real producers + 24 reference files, one table shape (400k rows), no Spark/parquet-mr histories of their own, no bloom/page-index-heavy writers; DELTA_BINARY_PACKED/DELTA_LENGTH/DELTA_BYTE_ARRAY (DuckDB `V2`, 7.9 % of its corpus), repeated/nested leaves, GZIP/LZ4/Brotli (common in Hadoop-era data; Z3-05..08's deflate replay is the unlock) stay opaque or CDC; small nested control costs +14 % (recipe overhead on 220 KB). Small ranges cost a page (carry-forward: per-page Snappy fragment-size index); objects ×9.8 vs CDC and 96 B/ref set the group target. Predictors are verified per page, never trusted by producer name; a CRC-hash Snappy build or new dictionary policy is a new id or an explicit page. **I3:** admit flat Parquet from first sight (logical already wins first sight), keep CDC for unsupported files, ids as a versioned registry, `KindParquet` 10 is lab only. The page-granular, predictor-id design generalizes to ORC/Arrow stripes (not implemented).
