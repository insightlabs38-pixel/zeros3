# M5-A: SigV4 query authentication, presigning, virtual-hosted addressing

External, black-box proof that ZeroS3's SigV4 query-string authentication
(presigned URLs), `zeros3 presign` CLI, and virtual-hosted-style addressing
interoperate with a real, unmodified AWS SDK for Go v2 client — not a
ZeroS3-specific presign workflow. Every presigned URL fetched/uploaded in
this harness is generated by the SDK's own `s3.PresignClient` and then
sent with an ordinary `net/http.Client` carrying no S3-specific signing
logic of its own.

## What the harness proves

### Presigned GET (positive)

`s3.PresignClient.PresignGetObject` against a path-style endpoint,
fetched with `http.DefaultClient.Do` (no SDK involvement in the actual
request): exact status, byte equality, SHA-256 equality, and
`Content-Type` preservation.

### Presigned GET (negative)

Each of the following, generated from one valid presigned URL and then
corrupted exactly one way, was confirmed to be rejected (non-2xx):
altered object path, altered bucket, a modified signed query parameter,
a modified signature, a modified `Host` header, an expired URL (1-second
expiry, checked after a 2-second sleep), and a presigned URL generated
under the wrong credential scope (a client configured for `eu-west-1`
against a server configured for `us-east-1`).

### Presigned PUT (positive)

`s3.PresignClient.PresignPutObject`, uploaded with a plain
`http.Client`, then verified through an ordinary **signed** `GetObject`
and `HeadObject` — byte equality, SHA-256 equality, and
`Content-Length`.

### Presigned PUT (negative) — mutation safety

Each negative case (tampered path, tampered signature, modified `Host`,
expired URL) was independently confirmed via `HeadObject` to leave the
target key **completely absent** — no partial write, no visible mutation,
for every rejected presigned PUT.

### `zeros3 presign` CLI

The `zeros3` binary's own `presign get`/`presign put` subcommands were
invoked directly (`exec.Command`, capturing stdout), and the resulting
URLs were used exactly like SDK-generated ones: a CLI-generated presigned
PUT succeeded, a CLI-generated presigned GET returned the exact uploaded
bytes, and neither URL was found to contain the raw secret access key.

### Virtual-hosted-style addressing

The server was started with `-vhost-base s3.zeros3-harness.test`. A
second SDK client (`UsePathStyle: false`, `BaseEndpoint` pointing at that
vhost domain) was built with a redirect-dialing `http.Transport`
(`DialContext` always dials the real `127.0.0.1:<port>` regardless of the
requested hostname, while the `Host` header — and therefore what SigV4
signs — is left exactly as constructed) — the standard technique for
exercising virtual-hosted-style addressing without needing real DNS for
the test domain; a real deployment would use actual DNS instead of this
dial redirect, with no change to ZeroS3 itself. Through that client:
ordinary signed `PutObject`/`GetObject` round-tripped correctly, a
virtual-hosted-style presigned URL (`bucket.<domain>` in `Host`, not in
the path) was generated, fetched, and verified byte-for-byte, and the
`zeros3 presign -vhost` CLI flag produced a working virtual-hosted-style
presigned PUT.
