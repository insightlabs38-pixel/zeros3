## Harness

`testing-harnesses/harness/m8_baseline/main.go`. Talks to a real `zeros3`
server subprocess three ways, matching the M8 task's "local ZeroS3
subprocesses" / "black-box" requirement:

- **AWS SDK for Go v2** (pinned, black-box S3 client) for B1/B2/B3/B4/B5
  (PUT/GET/CopyObject) and for populating B8's fixture.
- the real **`zeros3` CLI subprocess** (`os/exec`, never Go package
  internals) for B6 (`sync`), B7 (`stats -json` / `verify -json`).
- direct process start/stop/timing for B8.

All content is generated by a small deterministic linear-congruential
generator (`deterministicBody`, seeded per-scenario) — reproducible
across OS/architecture, **not compressible or repetitive** (labeled
per-scenario below). ZeroS3 has no compression stage, so this doesn't
affect physical-byte results; it matters only for the "record whether
content is compressible" requirement.

### Exact command

```sh
cd testing-harnesses
go build -o m8_baseline ./harness/m8_baseline/
CGO_ENABLED=0 go build -trimpath -buildvcs=false -ldflags="-buildid=" -o zeros3 zeros3.go   # in the zeros3 checkout, at eaec1adc
./m8_baseline -bin /path/to/m7-gold/zeros3 -out /tmp/m8-baseline-run
```

Full raw stdout of the recorded run is reproduced verbatim in each
scenario section below (nothing paraphrased).

## B1. Ordinary PUT

Deterministic pseudo-random content (non-compressible, non-repetitive).
Fresh store, one object per size, `bench` bucket.

| Size | Wall time | Effective throughput | Physical chunk payload | Chunk count |
|---|---|---|---|---|
| 16 MiB  | 690 ms  | 23.2 MiB/s | 16.00 MiB  | 254  |
| 64 MiB  | 2.852 s | 22.4 MiB/s | 64.00 MiB  | 1000 |
| 256 MiB | 18.27 s | 14.0 MiB/s | 256.00 MiB | 4029 |

Physical chunk payload equals logical size in every case, as expected —
every byte of a brand-new, never-before-seen object is unique. The
16 MiB→64 MiB step scales roughly linearly; the 256 MiB step is
noticeably slower per MiB, consistent with `zeros3.go`'s documented
known issue that the entire request body is buffered in memory before
CDC chunking begins (Section "Known issues" in `STATUS.md`), not a CDC
algorithmic problem — see Caveats and the file-per-chunk-CAS conclusion
below. The 1 GiB scenario was not run in this pass (kept the harness
within a reliable hackathon-scale runtime budget; `-big` flag exists to
enable it).

## B2. Ordinary GET

Retrieves the exact objects B1 wrote; SHA-256 of the retrieved body is
compared byte-for-byte against the source content's own hash.

| Size | Wall time | Effective throughput | Checksum match |
|---|---|---|---|
| 16 MiB  | 835 ms | 19.2 MiB/s | true |
| 64 MiB  | 783 ms | 81.7 MiB/s | true |
| 256 MiB | 3.547 s | 72.2 MiB/s | true |

Every GET reproduced byte-identical content. GET throughput is higher
than PUT's at the larger sizes (read path has no CDC/hashing-while-
buffering cost the same way ingest does) — consistent with, not a
contradiction of, the PUT-side buffering note above.

## B3. Duplicate PUT / CAS reuse

The exact 256 MiB object from B1, PUT again under a new key
(`dup-of-put-268435456`).

```
logical_bytes=256.00 MiB  new_physical_chunk_bytes=0 B  wall=5.755s  reuse=100.0%
```

Zero new CAS bytes were written — every chunk the second PUT produced
already existed by content hash. **This is not the same claim as "zero
network transfer":** the AWS SDK still sent the full 256 MiB request
body over the wire, and the server still ran CDC chunking and hashing
over the whole body before discovering every chunk already existed
(hence wall time close to, even slightly above, B1's original 256 MiB
PUT — dedup here saves disk writes, not upload bandwidth or CPU chunking
work). See the M6 local-delta-sync (B6) and M8A remote-delta numbers for
where actual transfer avoidance is the point.

## B4. Edited-object CDC reuse

Deterministic 64 MiB base fixture; three edited variants (a 4 KiB
insertion at the midpoint, an 8 KiB deletion at 1/3, a 4 KiB in-place
mutation at 2/3), each PUT under its own key into the same store as
`base` (so "shared" below means "shared with `base`," which so far
dominates the store).

| Variant | Logical size | Unique bytes (this object) | Shared/reused | Exclusive/new | Reuse |
|---|---|---|---|---|---|
| base | 64.00 MiB | 64.00 MiB | 0 B | 64.00 MiB | 0.0% |
| insertion | 64.00 MiB | 64.00 MiB | 63.88 MiB | 122.37 KiB | 99.8% |
| deletion | 63.99 MiB | 63.99 MiB | 63.78 MiB | 214.55 KiB | 99.7% |
| mutation | 64.00 MiB | 64.00 MiB | 63.84 MiB | 165.32 KiB | 99.7% |

This is the CDC edit-locality story `TestDedup_EditedObjectReuseBeatsFixedSizeChunking`
(internal) and `harness/m3/dedup` (external, ~97.5%) already establish;
this run's ~99.7–99.8% reuse is consistent with (a bit higher than,
for this specific fixture shape) those numbers, not a new or
contradictory result — DEMO.md's own rehearsed ~99.9% figure is in the
same range. `base`'s own row is 0% by construction (nothing preceded it
in a fresh store); the edited variants' reuse is against everything
already in the store, which here is essentially just `base`.

## B5. CopyObject

The same 256 MiB object, copied within the same bucket.

```
logical_object_size=256.00 MiB  new_payload_chunk_bytes=0 B  wall=27ms
```

Zero new **payload chunk** bytes (the claim `zeros3.go`/README actually
make) and a 27 ms wall time — a manifest-and-journal-only operation, no
chunk I/O at all, exactly as CopyObject's own doc comment (section 11 of
`zeros3.go`) describes. Not "literally zero bytes written": a new
manifest file (and journal record) is still created for the copy's own
version identity.

## B6. M6 local delta sync

64 MiB deterministic local file, synced to a fresh store; then a 4 KiB
localized in-place edit; then re-synced.

```
--- initial sync (wall=3.708s) ---
Logical scanned:     64.00 MiB
Chunks:              1004
Chunks reused:       0
Uploaded payload:    64.00 MiB (1004 unique chunks)
Transfer avoided:    0 B
Reuse:               0.0%
--- second sync after localized edit (wall=996ms) ---
Logical scanned:     64.00 MiB
Chunks:              1004
Chunks reused:       1003
Uploaded payload:    217.66 KiB (1 unique chunks)
Transfer avoided:    63.79 MiB
Reuse:               99.7%
```

The second sync **actually avoided transferring** 63.79 MiB of the
64 MiB file (99.7%) — only the one edited chunk's bytes crossed the
wire, and wall time dropped from 3.7 s to ~1 s accordingly. This is the
comparison baseline M8A (remote-to-remote delta) is measured against in
Phase 3 (`R9`): M8A must show the same "only the missing chunks travel"
property between two independent servers, not just between a local file
and one server.

## B7. Verify

Run against store1 (populated by B1–B5: 9 live objects/manifests, 6258
chunk references after the dup/copy scenarios).

| Mode | Wall time | Manifests checked | Chunks checked | Journal frames | OK |
|---|---|---|---|---|---|
| basic | 146 ms | 9 | 6258 | 10 | true |
| deep  | 9.445 s | 9 | 6258 | 10 | true |

Deep verify (byte-for-byte re-hash of every reachable chunk) is ~65x
slower than basic verify here, as expected for re-reading and re-hashing
every chunk's actual bytes rather than trusting on-disk presence. Both
completed well within a reasonable operational window for a store this
size.

## B8. Startup/replay

3000 objects (8 KiB each, 3000 `PutObjectRoot` journal records)
populated, server stopped, then restarted from a cold process.

```
populated store: 3000 objects, 3000 journal PutObject records
cold-start-to-ready wall time: 21ms
```

**21 ms** to become ready and start accepting connections after
replaying 3000 journal records. This is the key input to the "is
indexing/compaction actually needed" question M8 asks (without
implementing either): at this journal size, replay cost is
imperceptible. See conclusions below.

## Conclusions

- **Is file-per-chunk CAS currently a measured bottleneck?** Not
  obviously at these sizes. B1's per-MiB slowdown at 256 MiB (14.0 MiB/s
  vs. 22–23 MiB/s at 16–64 MiB) is consistent with the already-documented
  whole-body-buffering behavior (`STATUS.md`'s "Known issues": the
  request body is fully buffered before CDC chunking starts), not with
  CAS file I/O itself — B5's CopyObject (which *only* touches CAS-free
  manifest/journal writes) completed in 27 ms regardless of the 256 MiB
  logical size it described. No change is warranted from this pass
  alone (per the Phase 1 gate); a genuine "many small files" stress
  scenario (e.g. an object with 100k+ tiny chunks) was not separately
  measured here and would be the next thing to check if CAS-file-count
  overhead is ever suspected.
- **Is startup replay currently problematic?** No — 21 ms for 3000
  journal records. Extrapolating linearly, a store would need roughly
  1–2 orders of magnitude more journal records before replay time
  becomes user-noticeable. Indexing/compaction (explicitly out of scope
  for M8, per the task) is not motivated by this data at realistic
  hackathon/demo store sizes.
- **Is ordinary PUT/GET performance adequate?** Yes for this
  environment's purposes — double-digit MiB/s PUT, double-digit-to-
  low-triple-digit MiB/s GET, both correct (every checksum matched).
  Not benchmarked against a production NVMe array; see Caveats.
- **How large is the M6 delta-sync advantage?** Substantial and
  measured, not asserted: 99.7% of a 64 MiB file's bytes avoided
  transfer on a small localized edit (B6), consistent with B4's CDC
  edit-locality numbers. This is the number M8A's remote-to-remote
  delta replication needs to reproduce across two independent servers
  in Phase 3.

## Caveats

- Single run, shared/virtualized hackathon hardware, not a dedicated
  benchmark rig with isolated I/O — absolute MiB/s numbers will vary
  run-to-run and machine-to-machine; only the qualitative
  conclusions above (CDC reuse percentages, replay-time order of
  magnitude, dedup-vs-transfer distinction) are the load-bearing claims.
- 1 GiB PUT/GET was not run in this pass (harness supports it via
  `-big`, kept off by default to bound total runtime).
- B1–B5 share one store (so B3/B5's "reuse" numbers are relative to
  what B1 already wrote); B4/B6/B8 each use a dedicated fresh store to
  keep their own measurements uncontaminated. This is called out
  explicitly rather than left implicit.
- All content is deterministic pseudo-random (non-compressible,
  non-repetitive); ZeroS3 has no compression stage, so this only
  matters for the "record content shape" requirement, not for
  interpreting the byte counts above.
- These are cold, single-shot measurements (one run each), not averaged
  across repeated trials — reported as "observed," not as a
  statistically-hardened benchmark suite.
