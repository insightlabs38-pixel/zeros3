# Z4-P1C: small-object storage (active segments with inline manifests)

Verdict: **P1C_PRODUCTION_READY**
Base `origin/main` `5b9bcdd400dda1ca2e6147a54ff6853b1814ce67` (P1B PR #106 and P1A PR #105 `merged=true`; B2 PR #97 and drafts #80/#81 open, draft and untouched; no P1C work existed). Production diff: `zeros3.go` only (+1.7 kLOC, standard library only, `go.mod`/`deps-proof.txt` unchanged). Evidence: [`../z4/p1c/`](../z4/p1c/README.md). Method = the P0 `p0bench` driver: real server over HTTP, fresh store and process per repetition, every PUT replayed byte for byte in a fresh process (**all rows `verified:true`**), **interleaved A/B on this VM** (4 vCPU, ext4 on virtio, Go 1.27, load generator on the same CPUs), variant order alternating each round, median [min-max] of 3 rounds. ## 1. What changed, in one paragraph
A known-size PUT below 1 MiB (and every manifest up to 64 KiB, whatever the object size) no longer creates files. Its chunks and its manifest are **records of one append-only segment** `segments/<seq>.seg`, which is a *pack-v1 file prefix* (same header, same 44-byte record header, raw codec, no new record format, no CRC: the record's own SHA-256 is the torn-tail check). Concurrent requests share one `write` + one `fsync` (leader hand-off group commit, no timer, no helper goroutine). Records enter the locator only after the covering `fsync`; the journal frame, written afterwards, is still the commit point. A segment seals at 32 MiB by appending the pack-v1 index and footer and publishing `packs/<body_sha256>.pack` (hard link, locator swap, then unlink), i.e. it **becomes an ordinary pack**: readers, `verify -deep`, `gc`, `repack`, tiering and bundles need nothing new. Store level **11** (level 10 is reserved by draft #97) is raised before the first segment exists. Specs: [`FORMAT.md`](../z4/p1c/FORMAT.md), [`DURABILITY_MODEL.md`](../z4/p1c/DURABILITY_MODEL.md), [`COMPAT.md`](../z4/p1c/COMPAT.md).

## 2. The testing blind spot, corrected first
P1B moved the production default (objects >= 256 KiB write packs) and hid the consequence behind a global threshold override in the test binary; 76 root tests and 7 external harnesses assert loose files. P1C removes the override: **the test binary runs the production default**, and a layout is chosen per test:
* `useLooseLayout(t, reason)` (explicit, reason recorded), `forEachLayout` (loose + production halves), `removeChunkAnyLayout` / `corruptChunkAnyLayout` / `tamperManifest` inject missing/corrupt faults into whichever representation holds the bytes (loose file, packed record, open segment after sealing it), `layoutObserver` + `ZEROS3_LAYOUT_MATRIX_OUT` record which physical representation each test really produced.
* Audit of the 76 ([`results/p1b_layout_audit.md`](../z4/p1c/results/p1b_layout_audit.md)): **30 are layout-independent** (verify/repair/GC/restore behaviour; they now run on the production layout unchanged) and **46 are explicit loose** with a reason. `TestLayoutMatrix_*` states integrity, repair findings, restart, history/restore/delete + gc, GC reclamation + repack and 8-way concurrency **once and runs them on loose and production for 8 KiB, 120 KiB, 700 KiB and 2 MiB objects**.
* Harness runner: policy printed per harness (`layout=loose|production`); `-force-production` runs everything on the default. External harnesses on the explicit loose policy: m3/dedup, m8f/conditional, z2_packed_cas, z2_pack_compression, m8d/fork, m8e/snapshot, z2_consumer(invariance, browser), m8b/repair, m8c/namespace_replication, and the `compact`, `compression`, `history-life`, `tier-life` validate stages (exact format-level / loose-file assertions); everything else (s3, sync, client SDKs, vectors, apps, bulk, bundle, tier, locality, cas-batch, direct-pack) runs the production default.
* Result: **root suite under the production default: 1,170 top-level tests pass** (`results/layout_matrix.jsonl.gz`, `layout_summary.txt`: of 1,155 default-layout test names 727 produced segment records, 507 packs, 632 loose chunks and 330 manifest files; 142 names are explicit-loose).

* A (shared sealed pack, manifests still files) and B (segment, manifests still files) reach only **1.1-1.7x**: the manifest file keeps one create + fsync + rename + directory entry per object. **Inline manifests are what makes the gain compelling** (A+/C: 2.8-10.8x). C is ahead of A+ in every cell (1.1x at c32, 1.9-2.4x at c1-c8) and needs no new file per commit group: A+ writes one pack per group (751 packs per 3,000 objects at c8, one per object at c1), which re-creates the many-small-packs scaling problem and the 200k-pack cliff; C has 1 segment per 32 MiB.
* **Sharded active segments do not help**: 2 segments 7.2k ops/s (1: 7.2k, 4 segments 5.9k) at c8; c32 18.9k vs 18.2k, 4 segments 11.3k (`proto_shards.jsonl`). One active segment, no global lock beyond the leader hand-off. Seal cost is negligible (2 MiB vs 32 MiB segments: 7.26k vs 7.28k ops/s); GOMAXPROCS 1/2/4: 932/1161/1158 -> 5410/6917/7452 ops/s.
* **Natural batching is enough**: a fixed batching window only adds latency (table in the generated tables, `proto_delay.jsonl`).
* The P1B proposal's CRC32C was not adopted: content addressing already gives the torn-tail check and the same bytes make a sealed segment a byte-valid pack-v1 file.

## 4. Design as implemented (details in the specs)
* **Group commit** (`segMgr.commit/lead/runBatch`): bounded queue (4096) and batch (256 requests / 8 MiB), one `WriteAt` + one `fsync`, dedup against the locator and inside the batch, records visible after the `fsync`, release, then the existing journal group commit. A failed `write`/`fsync` fails the whole batch, truncates the tail back, **retires** the segment (never fsynced again) and the next batch uses a fresh one; a leader panic fails its batch and hands leadership on. Data that was appended but never committed stays as dead records (no in-place rollback; `repack` reclaims it).
* **Lifecycle**: created (header + fsync + `segments/` fsync before first use) -> active -> sealed (tail, fsync, `verifyPackExact`, hard link into `packs/`, fsync, locator swap, unlink, fsync) -> ordinary pack. Rollover at 32 MiB (hard cap 64 MiB), at most 2 background seals, clean close seals from 8 MiB and otherwise leaves the segment open for re-adoption (no tiny pack per restart).
* **Recovery** (`recoverSegments`): complete sealed file -> finish the rename; unusable/never-used -> delete; otherwise the valid record prefix is kept (every record re-hashed, overflow-checked), the tail is copied to `tmp/seg-torn-*` (bounded to 15 files, removed by `gc`) and cut, the newest segment below target is re-adopted and the others sealed. Scan work is bounded by the segment size.
* **Ownership**: appending, truncating and sealing belong to one process (`segments.lock`, non-blocking flock; same-process re-opens share it). `stats`, `verify`, `doctor`, `versions`, `repair` and bundle export open with `OpenStoreShared`: they index the durable prefix read-only, re-resolve when the owner seals, and **cannot disturb a live server or steal ownership from one that starts later** (`TestP1C_SharedOpenerNeverDisturbsALiveWriter`, `TestP1C_CLIReadersAgainstALiveServer`).
* **Reads**: manifests by the journal-recorded SHA-256 (`loadManifestBytes`, content-verified like any chunk, file fallback); reads retry once on a fresh locator when a segment sealed underneath them. **Maintenance** (`gc`, `repack`, `compact`, `tier move/rebalance`, `reloadPacks`) quiesces the writer and seals first; the live set includes every live manifest SHA, usage statistics keep manifest records out of chunk counts (`packed_live_manifest_records`), `stats` counts inline manifest bytes as manifest bytes and open-segment bytes in `chunk_store_file_bytes`.
* **Policy/knobs**: `ZEROS3_SMALL_OBJECT_STORAGE=off` writes loose again; `ZEROS3_SEGMENT_TARGET_MIB`, `ZEROS3_SEGMENT_MAX_KIB` (default 1024: 256-768 KiB objects gain 16-30% over one pack per request, `results/seg_threshold.jsonl`). Unknown-size streams still use loose chunks; objects >= 1 MiB keep P1B's direct packs (their manifest is inline).
* **Also fixed (found while profiling)**: every PUT allocated and zeroed a 512 KiB CDC buffer (552 KB/op, 13% of server CPU at 4 KiB); it is now pooled (25 KB/op). Reported separately in the ablation so the storage-layer gain is not conflated with it.

* **Open time and RSS grow (+34% / +37% at 1M)**: every small object is now two locator records (chunk + manifest, 54.6 B each steady state; synthetic locator: 10M records = 522 MiB heap, 4.0 s build, 531 ns hit lookup) instead of two files the kernel keeps; RSS is the process high-water mark while opening (journal replay and locator build). This is the price of the layout, it is **not** unbounded (linear in records, no per-segment growth), and a persistent locator checkpoint is the recommended follow-up if tens of millions of objects matter. Pack count stays tiny: 147 files for 1M objects, so the P1B 200,000-pack cliff is gone (a pack is created per 32 MiB, not per request; a segment holds ~7,000 small objects).
* **Unclean-shutdown recovery** is the scan of one unsealed segment: **4 MiB 8 ms, 16 MiB 35 ms, 31 MiB 61 ms** (best of 3, `recovery_latency.txt`; every record is re-hashed, so it is linear in the segment size, capped by the 64 MiB hard cap); a clean restart re-adopts the segment the same way.
* **Reclamation under churn** (100k x 4 KiB, 50% / 90% deleted, history pruned): P1B `gc` reclaims per chunk file (1,043 -> 656 MiB in 14.0 s; 1,060 -> 364 MiB in 21.9 s). P1C `gc` frees nothing (it only drops fully dead packs; 1.6 s), `repack -apply` reclaims (518 -> **413 MiB** in 3.3 s at 50%; 538 -> **121 MiB** in 2.3 s at 90%): **smaller than P1B at every stage, but reclamation needs `repack`** (documented in `docs/OPERATIONS.md`).

## 9. Interaction with P1A / P1B
Pack publication, `dirSync`, the journal `commitQueue` and the per-digest claims are reused unchanged; the segment writer takes no `Store.mu` and no claim; lock order `commitMu` -> `Store.mu` -> `Journal.mu` unchanged, `segMgr.mu` and `packMu` are leaf locks held for microseconds. Medium objects keep P1B's direct packs from 1 MiB. P1B's pack-count valve (200,000) is untouched and no longer reachable for small objects.


## 12. Compatibility and the format floor
[`COMPAT.md`](../z4/p1c/COMPAT.md) lists 19 situations with the test or evidence for each. Level **11**, raised immediately before the first segment file (after the tier roots any level above 5 implies; never lowered; never raised if no segment is created; `supportedStoreFormat` = 1..9 and 11 so a level-10 store of draft #97 is still refused). **Older binaries refuse a level-11 store** (verified with the real P1B binary: `unsupported store format version 11 (this build supports versions 1 through 9)`, store tree unchanged, `results/compat_old_binary.txt`; the same binary reads a store written with the policy off and a store the new binary only opened). Stores that never write a small object, or run with `ZEROS3_SMALL_OBJECT_STORAGE=off`, keep their level. Policy off after segments exist: still readable, recoverable, maintainable. A sealed segment is a byte-valid pack-v1.

## 13. Crash and fault qualification
* **Deterministic crash matrix** (`TestP1C_CrashMatrix_Segments`): 144 cases = {1, 6, 16 concurrent PUTs + 8 sequential} x 16 boundaries (segment create, dir sync, before/after write, before/after fsync, locator publish, seal write/sync/link/dir-fsync/unlink, manifest, journal write/sync, apply) x Nth firing; 100 injected a crash. After the crash every goroutine dies at its next hook, the crashed files are copied and recovered; checks: every acknowledged object byte-identical, nothing half-visible, `verify -deep`, `gc`, no stuck leader/queue/seal goroutine, every unacknowledged PUT retryable.
* **Power-loss state model** (`TestP1C_CrashStateModel`): at 31 boundary snapshots taken from a running store, the directory is degraded 7 ways (as written; volatile suffix dropped; torn midway; zero-filled hole in front of later bytes; new segment's directory entry lost; pack name not persisted although the segment carried its footer; segment name resurrected after the seal) = **217 recovered states**, each checked for acknowledged-data intact, nothing visible but unreadable, `verify -deep`, writability and idempotent second recovery. It models which bytes may be missing at each barrier; **it is not a block-device fault test (none is available here) and no power-loss claim on real hardware is made.**
* **Failure injection**: fsync error and short write (batch fails as a unit, writer recovers on a fresh segment, restart clean); the failing batch fails all members and spares the next; 7 torn-tail shapes (partial header, header without payload, partial payload, complete record with wrong digest, zero hole, absurd length, garbage), 4 unusable segment shapes; corrupt live chunk/inline manifest makes maintenance refuse and the damage stays visible to `verify -deep`; read-only openers vs a live writer (in-process and `zeros3` subprocesses); seal under concurrent readers; hard-cap rollover.
* **Real `kill -9`** (`TestP1B_RealKill_*`, 12 clients, random kill moments, 6 rounds on one accumulating store): default policy, **`segments-small-objects`** (100 B - 200 KiB objects, 1 MiB segments so kills land in appends, rollovers and seals) and loose-only: every acknowledged object byte-identical, `verify -deep` OK, `gc` keeps all.
* **Ordering audit of a real server** (`strace -f -y`, `results/audit_summary.txt`): rules S1-S5 (one write+fsync per group, journal write only after the covering fsync [sequential mode], header+directory fsync before first record, sealed tail fsynced before the link and `packs/` fsynced before the unlink, `FORMAT.json` + root fsync before the first segment) hold on a sequential and a concurrent trace; **five negative controls (a barrier removed from the real trace) are each detected**. Ordering evidence, not a device experiment.
* `go test -race ./...` PASS (1,073 s; the first race run found one real data race, `Verify` reading `s.format` while the first segment raised the level, fixed by `formatSnapshot` and covered by `TestP1C_FormatRaiseIsRaceFreeAgainstReaders`).

## 15. Rejected alternatives
Shared sealed packs per commit group (many small packs, 1.1-1.7x without inline manifests); sharded/multiple active segments (no gain at c8, worse at c32); unified journal+segment log (changes the commit authority, not needed for the gain); a new CRC32C record (redundant); fixed batching windows (latency only); manifests in the journal frame (memory); a persistent locator checkpoint (not needed at the measured scales, recommended next if 10M+ objects matter); `O_TMPFILE`; raising the segment threshold above 1 MiB (no gain from 1 MiB, `seg_threshold.jsonl`).

## 16. Regressions and costs
* **Older binaries refuse a level-11 store**; the default policy makes the first small PUT raise a fresh store to level 11 (tier roots are created at the same time). `ZEROS3_SMALL_OBJECT_STORAGE=off` avoids both. Level 10 stays free for draft #97.
* Open-time RSS/time +37% / +34% at 1M objects (section 8); `gc` alone no longer reclaims partly dead small-object data (`repack` does); a restart below 8 MiB keeps an open segment that the next open re-hashes (bounded by the segment size).
* Memory per in-flight small request: a copy of its chunks (up to 1 MiB) until the group commit returns.
* ~1.7 kLOC of production code and four new knobs. Defects found and fixed during qualification (by the new tests or by tracing every `OpenStore` caller): a concurrent `verify`/`stats` could have truncated or sealed a live writer's segment (now ownership-gated), `tier move -all` mistook a segment for a pack, a read could meet a vanished file during a seal (hard link first, retry), the first segment broke the reopen of stores below level 5 (tier roots now created first), a hard-cap/empty segment appeared as a missing pack in `verify`.
* Not tested: real block-device power loss; filesystems without hard links (fallback to rename is implemented, not exercised on such a filesystem); fsync latency of slow devices.

## 17. Remaining bottlenecks and recommendation
At 4 KiB c8 the server now spends ~27-35% of its CPU in syscalls (two sequential fsyncs per group: segment, then journal), ~10% in SigV4 HMAC, ~10% in journal group commit and JSON; allocation is 25 KB/op. Folding the journal frame into the segment commit (one fsync) would change the commit authority and is not recommended without a new durability review. Recommended next steps, in order: **P2** (manifest cache, GET/range behaviour, allocation, read concurrency; small GETs already gain 13%), a **persistent locator checkpoint** if the 10M+ object regime matters, and a **block-device fault harness** to turn the crash-state model into power-loss evidence.
