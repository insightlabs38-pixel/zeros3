## 1. What changed, in one paragraph
A known-size PUT below 1 MiB (and every manifest up to 64 KiB, whatever the object size) no longer creates files. Its chunks and its manifest are **records of one append-only segment** `segments/<seq>.seg`, which is a *pack-v1 file prefix* (same header, same 44-byte record header, raw codec, no new record format, no CRC: the record's own SHA-256 is the torn-tail check). Concurrent requests share one `write` + one `fsync` (leader hand-off group commit, no timer, no helper goroutine). Records enter the locator only after the covering `fsync`; the journal frame, written afterwards, is still the commit point. A segment seals at 32 MiB by appending the pack-v1 index and footer and publishing `packs/<body_sha256>.pack` (hard link, locator swap, then unlink), i.e. it **becomes an ordinary pack**: readers, `verify -deep`, `gc`, `repack`, tiering and bundles need nothing new. Store level **11** (level 10 is reserved by draft #97) is raised before the first segment exists. Specs: [`FORMAT.md`](../z4/p1c/FORMAT.md), [`DURABILITY_MODEL.md`](../z4/p1c/DURABILITY_MODEL.md), [`COMPAT.md`](../z4/p1c/COMPAT.md).

## 2. The testing blind spot, corrected first
P1B moved the production default (objects >= 256 KiB write packs) and hid the consequence behind a global threshold override in the test binary; 76 root tests and 7 external harnesses assert loose files. P1C removes the override: **the test binary runs the production default**, and a layout is chosen per test:
* `useLooseLayout(t, reason)` (explicit, reason recorded), `forEachLayout` (loose + production halves), `removeChunkAnyLayout` / `corruptChunkAnyLayout` / `tamperManifest` inject missing/corrupt faults into whichever representation holds the bytes (loose file, packed record, open segment after sealing it), `layoutObserver` + `ZEROS3_LAYOUT_MATRIX_OUT` record which physical representation each test really produced.
* Audit of the 76 ([`results/p1b_layout_audit.md`](../z4/p1c/results/p1b_layout_audit.md)): **30 are layout-independent** (verify/repair/GC/restore behaviour; they now run on the production layout unchanged) and **46 are explicit loose** with a reason. `TestLayoutMatrix_*` states integrity, repair findings, restart, history/restore/delete + gc, GC reclamation + repack and 8-way concurrency **once and runs them on loose and production for 8 KiB, 120 KiB, 700 KiB and 2 MiB objects**.
* Harness runner: policy printed per harness (`layout=loose|production`); `-force-production` runs everything on the default. External harnesses on the explicit loose policy: m3/dedup, m8f/conditional, z2_packed_cas, z2_pack_compression, m8d/fork, m8e/snapshot, z2_consumer(invariance, browser), m8b/repair, m8c/namespace_replication, and the `compact`, `compression`, `history-life`, `tier-life` validate stages (exact format-level / loose-file assertions); everything else (s3, sync, client SDKs, vectors, apps, bulk, bundle, tier, locality, cas-batch, direct-pack) runs the production default.
* Result: **root suite under the production default: 1167 top-level tests pass** (`results/layout_matrix.jsonl.gz`; `layout_summary.py`: 1154 default-layout names produced segment records in 729, packs in 505, loose chunks in 631, manifest files in 327; 141 explicit-loose names).

## 4. Design as implemented (details in the specs)
* **Group commit** (`segMgr.commit/lead/runBatch`): bounded queue (4096) and batch (256 requests / 8 MiB), one `WriteAt` + one `fsync`, dedup against the locator and inside the batch, records visible after the `fsync`, release, then the existing journal group commit. A failed `write`/`fsync` fails the whole batch, truncates the tail back, **retires** the segment (never fsynced again) and the next batch uses a fresh one; a leader panic fails its batch and hands leadership on. Data that was appended but never committed stays as dead records (no in-place rollback; `repack` reclaims it).
* **Lifecycle**: created (header + fsync + `segments/` fsync before first use) -> active -> sealed (tail, fsync, `verifyPackExact`, hard link into `packs/`, fsync, locator swap, unlink, fsync) -> ordinary pack. Rollover at 32 MiB (hard cap 64 MiB), at most 2 background seals, clean close seals from 8 MiB and otherwise leaves the segment open for re-adoption (no tiny pack per restart).
* **Recovery** (`recoverSegments`): complete sealed file -> finish the rename; unusable/never-used -> delete; otherwise the valid record prefix is kept (every record re-hashed, overflow-checked), the tail is copied to `tmp/seg-torn-*` (bounded to 15 files, removed by `gc`) and cut, the newest segment below target is re-adopted and the others sealed. Scan work is bounded by the segment size.
* **Ownership**: appending, truncating and sealing belong to one process (`segments.lock`, non-blocking flock; same-process re-opens share it). `stats`, `verify`, `doctor`, `versions`, `repair` and bundle export open with `OpenStoreShared`: they index the durable prefix read-only, re-resolve when the owner seals, and **cannot disturb a live server or steal ownership from one that starts later** (`TestP1C_SharedOpenerNeverDisturbsALiveWriter`, `TestP1C_CLIReadersAgainstALiveServer`).
* **Reads**: manifests by the journal-recorded SHA-256 (`loadManifestBytes`, content-verified like any chunk, file fallback); reads retry once on a fresh locator when a segment sealed underneath them. **Maintenance** (`gc`, `repack`, `compact`, `tier move/rebalance`, `reloadPacks`) quiesces the writer and seals first; the live set includes every live manifest SHA, usage statistics keep manifest records out of chunk counts (`packed_live_manifest_records`), `stats` counts inline manifest bytes as manifest bytes and open-segment bytes in `chunk_store_file_bytes`.
* **Policy/knobs**: `ZEROS3_SMALL_OBJECT_STORAGE=off` writes loose again; `ZEROS3_SEGMENT_TARGET_MIB`, `ZEROS3_SEGMENT_MAX_KIB` (default 1024: 256-768 KiB objects gain 16-30% over one pack per request, `results/seg_threshold.jsonl`). Unknown-size streams still use loose chunks; objects >= 1 MiB keep P1B's direct packs (their manifest is inline).
* **Also fixed (found while profiling)**: every PUT allocated and zeroed a 512 KiB CDC buffer (559 KB/op, 13% of server CPU at 4 KiB); it is now pooled (25 KB/op). Reported separately in the ablation so the storage-layer gain is not conflated with it.

## 12. Compatibility and the format floor
[`COMPAT.md`](../z4/p1c/COMPAT.md) lists 19 situations with the test or evidence for each. Level **11**, raised immediately before the first segment file (after the tier roots any level above 5 implies; never lowered; never raised if no segment is created; `supportedStoreFormat` = 1..9 and 11 so a level-10 store of draft #97 is still refused). **Older binaries refuse a level-11 store** (@@OLDBIN@@). Stores that never write a small object, or run with `ZEROS3_SMALL_OBJECT_STORAGE=off`, keep their level. Policy off after segments exist: still readable, recoverable, maintainable. A sealed segment is a byte-valid pack-v1.

## 13. Crash and fault qualification
* **Deterministic crash matrix** (`TestP1C_CrashMatrix_Segments`): 144 cases = {1, 6, 16 concurrent PUTs + 8 sequential} x 16 boundaries (segment create, dir sync, before/after write, before/after fsync, locator publish, seal write/sync/link/dir-fsync/unlink, manifest, journal write/sync, apply) x Nth firing; 99 injected a crash. After the crash every goroutine dies at its next hook, the crashed files are copied and recovered; checks: every acknowledged object byte-identical, nothing half-visible, `verify -deep`, `gc`, no stuck leader/queue/seal goroutine, every unacknowledged PUT retryable.
* **Power-loss state model** (`TestP1C_CrashStateModel`): at 31 boundary snapshots taken from a running store, the directory is degraded 7 ways (as written; volatile suffix dropped; torn midway; zero-filled hole in front of later bytes; new segment's directory entry lost; pack name not persisted although the segment carried its footer; segment name resurrected after the seal) = **205 recovered states**, each checked for acknowledged-data intact, nothing visible but unreadable, `verify -deep`, writability and idempotent second recovery. It models which bytes may be missing at each barrier; **it is not a block-device fault test (none is available here) and no power-loss claim on real hardware is made.**
* **Failure injection**: fsync error and short write (batch fails as a unit, writer recovers on a fresh segment, restart clean); the failing batch fails all members and spares the next; 7 torn-tail shapes (partial header, header without payload, partial payload, complete record with wrong digest, zero hole, absurd length, garbage), 4 unusable segment shapes; corrupt live chunk/inline manifest makes maintenance refuse and the damage stays visible to `verify -deep`; read-only openers vs a live writer (in-process and `zeros3` subprocesses); seal under concurrent readers; hard-cap rollover.
* **Real `kill -9`** (`TestP1B_RealKill_*`, 12 clients, random kill moments, 6 rounds on one accumulating store): default policy, **`segments-small-objects`** (100 B - 200 KiB objects, 1 MiB segments so kills land in appends, rollovers and seals) and loose-only: every acknowledged object byte-identical, `verify -deep` OK, `gc` keeps all.
* **Ordering audit of a real server** (`strace -f -y`, `results/audit_summary.txt`): rules S1-S5 (one write+fsync per group, journal write only after the covering fsync [sequential mode], header+directory fsync before first record, sealed tail fsynced before the link and `packs/` fsynced before the unlink, `FORMAT.json` + root fsync before the first segment) hold on a sequential and a concurrent trace; **five negative controls (a barrier removed from the real trace) are each detected**. Ordering evidence, not a device experiment.

## 15. Rejected alternatives
Shared sealed packs per commit group (many small packs, 1.1-1.7x without inline manifests); sharded/multiple active segments (no gain at c8, worse at c32); unified journal+segment log (changes the commit authority, not needed for the gain); a new CRC32C record (redundant); fixed batching windows (latency only); manifests in the journal frame (memory); a persistent locator checkpoint (not needed at the measured scales, recommended next if 10M+ objects matter); `O_TMPFILE`; raising the segment threshold above 1 MiB (no gain from 1 MiB, `seg_threshold.jsonl`).
