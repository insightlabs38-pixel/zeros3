## 1. Architecture
A **body record** `bodies/<sha256>.body` is the physical locator of one object *content*, not of a manifest/key/version. Once committed it is the liveness root and read source for every manifest with that SHA-256; the immutable, journal-hashed manifest keeps its CDC chunk list only as a *virtual* chunk index (hash+length) used by sync/bundles/replication. Forms: **pin** (explicit chunk list: a base kept alive with no namespace entry), **rep** (existing kind 1–12 root, unchanged format), **delta** (new `ZS3D` v1 exact COPY/ADD envelope, ≤4 bases, each carrying SHA-256+length; 128 KiB independently deflated frames give range-addressable decode). Records are `ZS3B` v1, CRC32C, immutable, replaced only by atomic rename at generation+1.
Why not the alternatives: rewriting manifests breaks journal manifest hashes; per-manifest locators cannot outlive their namespace entry (bases), and copies/versions/snapshots would each need their own. Keying by content makes copy, restore, version history and snapshots body-backed automatically (tests: copy, restore, history prune, snapshot, bundle).
Resolver: `authCtx` opens bodies once per request, enforces depth (record depth ≥ bases+1, hard 4), cycle, fanout (≤4) and a 512 MiB materialization budget; every physical chunk is SHA-verified by CAS, whole reads additionally prove length+SHA-256 at EOF (mismatch aborts the stream like the existing rep path). Ranges decode only the touched frames; REP ranges use the kind's native range decoder else a bounded materialization. A disposable per-store decoded-object cache (default off) never affects correctness. If a body is unreadable *and* CDC chunks still exist the read falls back to them (counted); after reclamation there is no fallback and the failure is explicit.

## 2. Transition and recovery state machine
S0 CDC → S1 components staged (unreferenced CAS chunks, batch-fsynced) → S2 *proof*: the candidate record is serialized, re-parsed, resolved through the production read path from the durable CAS (overlay for the unpublished record, published bases) and reconstructed to exact length+SHA-256 → S3 `authPublish`: closure check (bases committed with consistent size/depth, every component present at length), FORMAT floor raised+fsynced, tmp write+fsync, **one atomic rename**, directory fsync → S4 CDC eligible: reachability now roots the content through the body → S5 gc deletes loose chunks, repack rewrites partly dead packs. Revert: materialize+fsync CDC chunks (each verified against its manifest hash) → pin(gen+1) if dependents exist, else retire record.
No separate intent journal is needed: S3's rename is the only commit point of a single self-validating file, every earlier state is garbage-only, every later state is complete. (A journal would be required only to make *several* contents switch atomically together; they are independent here, and base pins commit first and are idempotent.) Injected-failure seam (`authFault`: ENOSPC at component write, short record write, pin) and malformed/over-deep/cyclic/stale records fail closed.
Real-process matrix (SIGKILL via test hook, fresh-process reopen, then completion of the interrupted operation): 18 boundaries / 27 kills — floor raise before/after, components flushed, proof done, record written/before-rename/after-rename/published (occurrence 1 and later), CAS stage-sync and rename, revert materialize/CAS/before- and after-retire, gc before-delete, before-pack-delete, pack-deleted, and closure import record/chunk points. After every kill all acknowledged objects read exactly and deep verify passes; resumed migrate/revert/gc/repack complete.

## 3. Dependency graph, GC and actual CDC retirement
Liveness = manifests (current, history, snapshots) → body → bases (transitively) → component chunks; `AuthLive/AuthOrphans` come from the same single reachability scan as stats/verify/gc. Any fault (missing/corrupt record or base, depth, cycle, size mismatch, missing component) makes the scan not-OK, **gc refuses**, and the manifest's CDC list is conservatively kept referenced. Orphan records are removed before their chunks. Tested with real files: shared components across objects, base kept alive only by a dependent after its namespace entry *and manifest* were pruned (`versions prune` + gc), whole chain reclaimed when the last dependent goes, mixed pin/rep/delta, snapshots, copy, concurrent PUT/overwrite/delete/copy/snapshot/read racing repeated migrations under `-race`, gc/repack crash points. Retirement is physical: store bytes fall (section 5) and the CDC chunks of delta objects are absent (`casStat` fails) while reads stay exact and `Verify(true)` reconstructs every body.
A component is reused without unrelated bytes or obsolete manifests (chunk granularity); a delta base is retained as a *whole* body, so unrelated bytes of a base stay while any dependent exists (flatten = revert to pin).

## 4. Compatibility floor, migration, rollback
Floor **10** (`storeFormatVersionAuthority`), raised durably immediately before the first record (a refused publication leaves it unchanged). Floor 9 cannot be reused: a 9-binary would open the store, treat manifest chunk lists as liveness and report retired chunks missing. Real old binary (built from `44d7d58`): `stats, verify, doctor, gc -apply, compact, repack, serve, versions` all refuse "unsupported store format version 10" with a byte-identical store tree; a store that never adopted authority stays at its old floor and old binaries open it. One existing test fixture used 10 as "future version"; it now uses 99 (intent unchanged). Authority is created only by `zeros3 authority migrate -apply` (offline, exclusive lock) or the in-process API; off by default. `authority revert` and `authority status` complete the lifecycle; no automatic downgrade of the floor.

## 5. Physical storage economics (real packs, after gc+repack+compact)
Method: each family is PUT into a fresh store (CDC, compacted into packs = baseline), a copy is migrated, `gc -apply` + repack(live<=100%) + compact + gc run, and `dirBytes` (packs, bodies, manifests, journal, FORMAT; excluding tmp) is summed. One fresh process per family. Corpora (`/tmp` scratch, URLs in harness): 3 coreutils tars, 12 Newtonsoft.Json DLLs (5 for "short"), 3 F-Droid APKs x 2 dex, 3 Git pack exports of this repo, plus *synthetic* pyarrow (zstd) Parquet and SQLite edit chains and 7 unrelated inputs. Rows are not B1 projections; B1's DEX/Parquet figures (0.49/0.40 structural) were **not** reproduced on these different inputs.

Findings. (i) Additive representations cost 1.5-1.9x CDC on disk: the sidecar model cannot save space, confirming B1. (ii) Retiring CDC makes B1's saving real: 0.50x for source archives, 0.72-0.82x for CLR, 0.82x Git, 0.27x for aligned DB states, nothing for unrelated data. (iii) Short and long CLR histories: 0.715x (5) vs 0.801x (12); one-off/unrelated inputs correctly stay CDC at 1.00x. (iv) Structural rep-only wins only where components recur: DEX 0.884x, SQLite 0.697x, CLR 0.897x (matches B1's 0.898), Parquet/Git/unrelated lose or tie; a lone first-sight rep is 1.01-1.16x CDC, so reps are admitted per *group* by union component cost (kinds seen once are never built). (v) Per-object greedy mixing was a failed experiment: `mixed` gave DEX 1.081x and CLR 0.921x (worse than delta-only 0.817x) because choosing delta for some members destroys the sharing the rep group was priced on; the default `best` strategy plans delta-only and rep-only and applies the cheaper (never worse than either). (vi) Depth 4 helps only aligned/tiny families (SQLite 0.275->0.269, CLR 0.715 vs 0.817 on short) at 1.3-1.6x read cost; default stays 2. (vii) Migration double storage: delta-only peaks 1.2-1.6x CDC; `best` peaks 3-4x because rep candidates are staged speculatively and only reclaimed by gc - a real inefficiency (singleton kinds are now skipped; estimating before flush is the fix). (viii) Bodies/records: 1.8 KB for 6 dex, ~0.3 KB/record plus 128 B sketch; manifests keep their CDC chunk lists (~0.1 % of logical bytes, not yet prunable).
Bounded decoded cache / "disposable CDC cache": RAM-only, default off, no disk copy; it removes repeat REP/base decode (warm == cold within noise for delta because the request-local piece cache already shares bases). A disk-materialized cache would be exactly `materializeCDC` output (unreferenced chunks that gc removes) and was not benchmarked. Raw rows: `testing-harnesses/z4/b2/economics.jsonl.gz`.

Delta-authoritative reads are 1.3-2.9x slower whole-object and 1.6-3.5x higher 4 KiB amplification than CDC (cold device reads were not measured; amplification counts logical CAS bytes). Two measured fixes: a request-local verified-chunk cache (whole delta reads 11-15 -> ~50 MB/s on CLR) and 32 KiB delta pieces (4 KiB amplification 107x -> 57x); 16 KiB frames cut 4 KiB latency (CLR 1.9 -> 1.1 ms, SQLite 1.6 -> 0.9 ms) at no size cost (0.849 vs 0.863; 0.276 vs 0.275) but are untested on literal-heavy tar; 1 MiB frames cost 7.3 ms on CLR. Default stays 128 KiB. Structural REP bodies are archive-only: DEX/SQLite 4K reads cost 50-640 ms and 13-96 MB/s whole (existing decoders; ranges fall back to bounded materialization when the kind has no range decoder), so the `hot` policy (measured 4K amplification <= 2x CDC, newest versions stay CDC, no REP) keeps 42-85 % of CDC whole-read throughput where it admits deltas (tar 164 vs 194 MB/s, DEX 121 vs 143, CLR 61-73 vs 132-144) while saving 0.73x (tar), 0.75x (SQLite), 0.76-0.82x (CLR) and refuses Git/Parquet (1.00x). Throughput noise between runs is about +/-25 %. 4 concurrent readers scale (e.g. tar 411 vs 855 MB/s CDC). A general S3 hot path must use the hybrid; archive mode accepts ~2x slower reads for up to 2x less disk.

## 7. Bundles, sync, replication, repair
Capability negotiation `AuthTransferMode(src,dst)`: native closure transfer only when both declare floor >= 10 and depth cap, otherwise exact bytes. *Native*: `ExportAuthorityClosure[Thin]`/`ImportAuthorityClosure` stream every record + component with per-chunk hashes and a trailing SHA-256; the importer verifies, makes chunks durable, proves each record by reconstruction and publishes bases first; truncated/bit-flipped streams install nothing; re-import is idempotent; SIGKILL at chunk/record/rename leaves a valid destination and the retry completes; thin streams omit bases the destination holds, are refused cleanly (`errAuthMissing`) if the base is absent, and the sender falls back to the full closure. *Exact materialization*: the unchanged CDC sync/bulk/replicate protocols read retired chunks by slicing them (hash-verified) out of the body through a virtual chunk index; negotiate treats them as present and `sync` commit re-materializes shared chunks physically. Verified: replicate of retired-CDC objects to a new-format store and to the **old binary**, with exact bytes and MD5 ETag; full bundle of a retired-CDC snapshot imported by the new binary and the old binary (old `verify -deep` passes, no floor carried); sync of a new revision into a body-only store. Gaps: native closure transfer is a library/stream, not yet a wire endpoint or advertised protocol capability; delta-bundle export shares the virtual-read path but has no dedicated test; no encoder-only state is needed anywhere in decode (fresh processes everywhere).
Repair: SHA-256 only *detects*. Missing/corrupt components are found by deep reachability/verify; a peer holding the same closure repairs them by digest through the existing `repair` (tested), a peer holding only ordinary objects cannot (explicit unresolved, verify stays failing, gc refuses); `AuthorityRepairObject` accepts exact bytes (checked against the content hash), rewrites the manifests' CDC chunks durably and supersedes the body with a pin at generation+1. With no valid source the object is unrecoverable and reported so; nothing is regenerated. Reliability tradeoff (measured, harness `blast_*`): losing one physical chunk breaks up to 12 contents in a 12-version delta chain (mean 3.2) versus <=2-4 for CDC (mean 1.0-1.6); depth<=2, redundant peers/scrubs and pins bound but do not remove this. Backups that today rely on "CDC is the redundant copy of a rep" lose that implicit repair source.

## 8. Resources and remaining inefficiencies
Isolated fresh processes: delta migration of 187 MB tar 5.9 s (delta-only) / 28.6 s (`best`), RSS 447-540 MiB (whole target + up to 8 candidate bases in memory; cap 256 MiB per object; DEX rep construction 107-131 s for 54 MB, RSS 496 MiB); reachability with bodies 0-2 ms, deep verify 0.1-2.3 s per 8-190 MB; gc+repack 1-13 s; record+sketch overhead ~0.4 KB/body; no persistent similarity index (B1's index is *not* integrated: candidates come from per-run bottom-16 sketches and same-key neighbours - O(objects) memory per run).
Prototype limitations (fixable engineering): whole-object delta encoding with a 256 MiB cap (needs windowed/streamed matching); speculative rep staging; CLI migration/gc need the exclusive lock (the in-process API is concurrency-tested, a background worker is not built); no pack-run read coalescing for pieces; `stats` reports logical CDC accounting; PUT of already-held content rewrites CDC chunks until gc; sync negotiation rebuilds the virtual index on demand (O(live manifests), 100 ms TTL); tier policy untested. Fundamental costs: higher blast radius, 2x read cost, floor-10 lock-in (old binaries cannot open), offline-only reclamation.

## 10. Verdict
**REP_AUTHORITY_VIABLE_FOR_SELECTED_KINDS.** The architecture is correct and complete enough to be a first-class physical store: atomic single-record commit, closure-checked publication, fail-closed liveness/GC, real CDC retirement with measured space recovery, crash-safe across 29 real kills, old-binary refusal, exact interoperability through bundles/replication to old binaries, explicit repair semantics. No fundamental safety or compatibility blocker was found. The *economics* are workload-specific: 0.27-0.50x for aligned DB states and source archives, 0.72-0.82x for CLR/Git histories, 0.88-0.90x for DEX/Parquet-like data, nothing for unrelated/entropic data; reads cost ~2x and blast radius grows with chain depth, so authority belongs to cold/archive tiers and to the *older* versions of hot histories (hybrid), not to the S3 hot path as a blanket default.

## 12. Production design and implications
Integration (each step independently mergeable, creation off by default): (1) reader/liveness/GC/verify for floor 10 with pin+rep forms, `authority status|revert`; (2) closure checks in publish, old-binary refusal gate and A4-style three-generation matrix on the production port; (3) delta form (depth<=2) plus `authority migrate` with hot/archive policies, best-of-two planning and speculative-staging estimate before flush; (4) background worker under the shared lock with an I/O budget, windowed/streamed encoder for objects >256 MiB, B1's persistent similarity index replacing per-run sketches, pack-run read coalescing and 16-32 KiB frames; (5) wire capability advert + native closure endpoint, authority-aware `stats`, online/generation GC. Qualification before any merge: real power-loss/fsync-fault runs, 10^5-10^6 object scale, tier interaction, soak with concurrent GC, large-object windows, cold-device read measurement, a published operator runbook (floor-10 irreversibility, revert path).
B3: content-keyed bodies make cross-format component sharing economically real once CDC retires, but only when planned per group (a lone rep costs 1.0-1.2x). B4: reversible synthesis can ride the same record/closure/proof/GC machinery as a new form at floor 11. B5: model gains are mostly predictor-only (B1 0.0025C); keep as an archive form, never a hot-path default. B6: codec ranking must price decode CPU, range support and blast radius - measured here as 2-3x amplification and 100x+ for non-range REP kinds. B7: planner needs group-aware costs, peak migration storage (3-4x observed), read-amplification probes (implemented) and a reliability term; greedy per-object choice demonstrably loses. B8: converge on CDC (hot, newest) + exact delta/rep for older versions and cold data behind floor 10, not a global switch.
