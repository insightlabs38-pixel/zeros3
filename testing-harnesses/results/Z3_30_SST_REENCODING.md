# Z3-30 — Exact SST re-encoding frontier: LevelDB, RocksDB, Pebble

Laboratory only; `zeros3.go`, tests, root `go.mod/go.sum`, ZS3R/ZS3T, Store format 6 and production kinds are untouched (diff empty). Code: `z3/snappyz3`, `z3/sstz3`, `z3/repz3/kinds/sst.go` (lab `KindSST` = 9), `z3/cmd/z3sst`, producers `z3/oracle/sst`. Starting `main` 70d2276.
**Question.** Can entry/value content hidden below unstable SST block boundaries be stored once, exactly, across flushes, compactions, splits/merges and sequence-number churn, at an honest reference/recipe price? **Yes for RocksDB and Pebble (Snappy/none tables); not worth it for LevelDB's own compactions.**
**Decisions.** RocksDB `PROMOTE_TO_I3` · Pebble `PROMOTE_TO_I3` · LevelDB `DEFER` · exact Snappy replay `CORE_PORTABLE` · one common exact SST decoder `YES`. Strongest result: RocksDB 8-state history 123.0 → 37.9 MiB (3.2×), unchanged-content rewrites 20.2 → 0.75 MiB. Strongest negatives: first sight costs +10 % (8 KiB groups), first-sight CDC admission locks the gain out (85.1 vs 37.9 MiB), LevelDB's own compaction already leaves CDC at par (22.6 vs 24.4 MiB).

## 3. Exact replay architecture
Parse → physical framing + exact decoded blocks → canonical records (user key, value; seq/type word kept apart) → record-hash-cut groups (`HashCutter`: cut decided by hash(user key)·size, target 8 KiB, max 32 KiB; no position dependence, tested) → content-addressed components. Recipe = per-block {stored size, 5-byte trailer, entry count, Snappy predictor or commands} + group record counts + seq/type words (delta/zigzag) + tail length + digests; **the footer, index, filters and properties are one opaque tail component** (0.66–1.28 % of table bytes, so never re-derived). Restart interval + maximal shared prefix reproduce **615 780/615 780** real blocks (0 explicit layouts); varint/prefix quirks are rejected by rebuild-and-compare. Decode needs only recipe + components + stdlib (no producer, no Snappy library). Rows `rt`: 577 tables × 6 forms = 3 462 round trips, length/SHA-256/bytes identical, 0 failures.

## 4. Exact Snappy (the Z3-18 blocker): closed
Explicit command recipes cost ≈ 190–210 commands/block = **12–13 % of table bytes** (82–86 MiB per producer corpus). A per-block *verified predictor flag* (re-encode the child with a deterministic reference encoder, compare with the stored bytes, keep commands on mismatch) leaves **0 explicit blocks of 551 389**: Pebble = Go snappy (186 172), LevelDB = C++ 1.1.10 (121 782 Go-identical + 58 241 with the masked 14-bit hash), RocksDB-bundled = same algorithm, 15-bit hash (124 670 + 3 363 + 57 161; found by sweeping hash widths over 4 433 blocks of 3–4 KiB). Recipe ≈ 1 B/block. Without predictors the same ukv costs +3.7 MiB first sight (+28 % vs CDC) and RocksDB sparse-update 6.7 vs 3.0 MiB (still 3× under CDC). Parse 184–190 MiB/s, command replay 374–388, predictors 150–395. Fuzz: 819 k execs (snappyz3) and 520 k (sstz3) clean.

Where the gain comes from: **RocksDB format 6 writes a different checksum into every block of every rewritten file**, so a content-identical rewrite shares 0 % of CDC chunks (1 447/1 447 payloads identical, 0/1 447 trailers) — splitting trailers from payloads alone ("exact blocks") already gives 20×; entry-level groups add insert/delete/split/merge immunity (native blocks shift; CDC and blocks lose, groups do not). Sequence churn (LevelDB/Pebble re-export): full internal key present in the old revision 0.0 %, (user key, value) pair 100 %; `full` pays 23 MiB, `ukv` (seq/type words in the recipe: 2.4 B/record LevelDB, 1.0 B Pebble/RocksDB, RocksDB zeroes them) pays 1.0. Key bytes are 2.5 % here: k/v split is 4 % cheaper at first sight and 34 % cheaper on renamed keys, but +1 % to +60 % on rewrites (a second reference per group) and ±3 % over the chain → KILL as default (revisit for small-value workloads). ## 10. Limitations and carry-forward
Generated, not public, histories (one value mix, 4 MiB tables, 4 KiB blocks, keys 2.5 % of bytes — small-value workloads where keys dominate are unmeasured and would favour k/v split); no range-del, value-block, merge or multi-column-family data; Pebble 2.x columnar and RocksDB > 6 untested; Zstd/LZ4 (common in tuned RocksDB) need `zstdz3` per-block replay behind a decompressed index (Z3-25 measured a 9–26 % metadata tax on big streams; 4 KiB blocks unmeasured) — adapter debt; object count (13×) and 96 B/ref decide the group target. **I3:** admit valid SSTs from first sight (greedy loses 2.2× on RocksDB), group target from the store's per-object cost, predictor ids as a versioned registry, `KindSST` number 9 is lab only. **Z3-31 (Parquet):** reusable primitives are the verified-predictor/explicit-fallback pattern and `snappyz3` for Snappy pages, record-hash cuts, and the checksum-in-recipe split; nothing Parquet is implemented here.
