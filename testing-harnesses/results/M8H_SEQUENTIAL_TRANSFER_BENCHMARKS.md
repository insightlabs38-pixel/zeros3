## Harness

`testing-harnesses/harness/m8h/bench/main.go`. Drives real `zeros3 serve`
subprocesses (two per replication scenario, one per repair/sync
scenario) via the real `zeros3` CLI (`replicate`/`repair`/`sync`/`verify`/
`stats`, `os/exec`, never Go package internals), with fixtures written
via the real AWS SDK for Go v2. Never calls into ZeroS3's Go package
internals; never modifies `zeros3.go`.

**Fixture generation.** All object content is generated by
`deterministicBody(seed, n)`: SHA-256 counter mode
(`SHA256(seed_be32 || counter_be64)` repeated), reproducible across OS/
architecture, non-compressible, non-repetitive. An earlier draft of this
harness used a plain power-of-2-modulus linear congruential generator
(the same one `harness/m8_baseline` uses) for speed; at the multi-
hundred-MiB scale this run needed, two LCG streams whose seeds land in
the same multiplicative coset become byte-identical (phase-shifted) from
their accidental intersection point onward, which silently fabricated
tens of megabytes of "already-present" chunks in what was supposed to be
an empty-destination scenario. This was caught by inspecting an
unexpectedly large `Transfer avoided` on a nominally-empty destination
(see "Methodology note" below), confirmed with a standalone collision
check, and fixed by switching to the SHA-256 counter-mode generator
before any numbers in this document were recorded. This is a benchmark-
fixture defect in this harness, not a ZeroS3 defect — no ZeroS3 code was
touched — but is recorded here in the interest of honest methodology.

**Known ZeroS3 limit encountered (not a bug):** `PutObject` rejects
bodies over `maxRequestBodySize` (256 MiB, already documented in
`STATUS.md`'s "Known issues" — the whole request body is buffered in
memory pre-CDC). This means a single ordinary `PutObject` of the
optional 1 GiB case-A fixture is rejected by ZeroS3 itself before
replication logic ever runs; B1 Case A below therefore covers 64 MiB and
256 MiB only. This is an existing, already-documented constraint, not a
new finding, and required no ZeroS3 change to work around (multipart
upload would side-step it but wasn't needed for what this measurement
answers).

**Repeats.** One untimed warmup run, then 3 measured runs per
configuration (5 for the cheapest, sub-5-second B1a/64MiB case). Median
reported as the headline number, with min/max shown for spread.

## B1 — M8A remote single-object replication

### Case A — destination completely empty

Two independent `zeros3 serve` processes (source, destination), fresh
random content per measured run (unique SHA-256-counter seed each time)
so the destination CAS genuinely lacks every chunk on every run.

| Size | Chunks | Median wall | Min | Max | Median throughput |
|---|---|---|---|---|---|
| 64 MiB | 966–983 | 3.97 s | 3.73 s | 4.21 s | **16.1 MiB/s** |
| 256 MiB | 3983–4014 | 16.20 s | 15.62 s | 16.24 s | **15.8 MiB/s** |

`Transfer avoided` was exactly 0 B on every run in this case, confirming
the destination was genuinely empty each time (not a self-dedup
artifact).

Average chunk size at 256 MiB (median run): 268,435,456 B / 4010 chunks
≈ **66.9 KiB** — close to CDC v1's 64 KiB target, as expected.

### Case B — partial reuse

A 128 MiB base object is first replicated into the destination (seeding
its CAS). Each measured source variant is `base-prefix(p%) +
fresh-random-suffix((1-p)%)`; the CDC-chunked prefix reproduces the
destination's existing cut points almost exactly, while the suffix is
freshly seeded per run so it's guaranteed missing.

| Target reuse | Actual `Transfer avoided` | Uploaded | Median wall | Median throughput (over uploaded bytes) |
|---|---|---|---|---|
| 25% | 33,512,488 B (25.0% of 128 MiB) | 100,705,239 B | 6.21 s | **15.5 MiB/s** |
| 75% | 100,642,324 B (75.0%) | 33,575,403 B | 2.71 s | **11.8 MiB/s** |
| 95% | 127,433,441 B (95.0%) | 6,784,286 B | 1.42 s | **4.6 MiB/s** |

The prefix-sharing fixture design hit its target reuse percentage almost
exactly at every level (25.0% / 75.0% / 95.0% actual vs. target),
confirming CDC content-defined chunking is doing what it's supposed to.

**Notable pattern:** throughput *drops* as the reused fraction grows,
even though less data is moving. Chunk count stays roughly constant
(~1985–1998 chunks) across all three because it's driven by the fixed
128 MiB logical size, not by how much is missing — so a fixed
per-object/per-negotiation overhead is being amortized over
progressively less actual payload. This matters: as ZeroS3's own CDC/CAS
value proposition succeeds (more reuse, less to move), this is exactly
the regime where a fixed sequential per-chunk cost becomes
*proportionally* more expensive, not less.

## B2 — M8C recursive namespace replication

Two shapes, each moving 512 MiB total logical payload across an empty
destination prefix each run (fresh random content per object per run).
The real (non-dry-run) `replicate -recursive` CLI prints no aggregate
stats to stdout (only `-dry-run` does) — "uploaded" here is measured the
same way M8's own baseline harness measures it: `zeros3 stats -json` on
the whole destination store, before and after each run (physical CAS
growth).

| Shape | Objects | Object size | Median wall | Planning (dry-run) | Median throughput |
|---|---|---|---|---|---|
| 32×16 MiB | 32 | 16 MiB | 31.72 s | ~0.16 s | **16.1 MiB/s** |
| 128×4 MiB | 128 | 4 MiB | 35.60 s | ~0.34 s | **14.4 MiB/s** |

Same 512 MiB logical payload, ~4x more objects → ~11% lower median
throughput and roughly double the (still tiny) planning time — visible
but modest per-object orchestration overhead on top of the dominant
per-chunk transport cost.

## B3 — M6 local delta sync

128 MiB local file, fresh store, initial full sync then a localized edit
(four independent 4 KiB mutations spread through the file) and a second
sync.

| Phase | Logical | Uploaded | Elapsed | Throughput |
|---|---|---|---|---|
| Initial sync | 128 MiB | 128 MiB (full) | 8.22 s | **15.6 MiB/s** |
| Edited sync | 128 MiB | 379.4 KiB | 1.83 s | **0.20 MiB/s** |

The edited sync's "throughput" collapsing to 0.2 MiB/s is expected and
not itself evidence of a transport problem: only ~380 KiB of *real*
payload moved in 1.83 s, and that wall time is dominated by re-scanning
and re-CDC-hashing the entire 128 MiB local file plus negotiating
~2000+ chunk digests against the remote store — i.e. **planning/
local-scan cost**, not chunk transport. This is the one scenario in this
report where the fixed per-sync overhead, not sequential transport,
plausibly explains most of the wall time for a small edit.

## B4 — M8B repair

64 MiB object (~980–1020 chunks depending on run), 1/16/64/256 chunks
deliberately corrupted then repaired from a healthy peer. `repair`
always finishes with a mandatory deep `Verify` over the whole store; a
matched deep-verify-only baseline (same object, no corruption) is
subtracted to isolate the peer-fetch-and-publish cost from that fixed
tax.

| Bad chunks | Of total | Payload fetched | Repair wall | Verify-only baseline | Fetch-attributable time | Per-chunk (attributable) | Throughput (fetched bytes / total wall) |
|---|---|---|---|---|---|---|---|
| 1 | 982 | 84.71 KiB | 931 ms | 697 ms | 234 ms | 234 ms | 0.09 MiB/s |
| 16 | 963 | 1.04 MiB | 961 ms | 679 ms | 282 ms | 17.6 ms | 1.08 MiB/s |
| 64 | 1011 | 3.64 MiB | 1089 ms | 714 ms | 375 ms | 5.9 ms | 3.34 MiB/s |
| 256 | 1020 | 15.95 MiB | 1388 ms | 673 ms | 715 ms | 2.8 ms | 11.5 MiB/s |

Two things stand out. First, the **mandatory post-repair deep verify is
a large, roughly constant ~0.7 s tax regardless of how much was actually
broken** — for the 1-bad-chunk case it's the majority of total wall
time. Second, **per-chunk attributable repair cost falls from 234 ms
down to 2.8 ms as the batch grows** — a classic fixed-per-request-
overhead signature: small batches pay a large fixed cost per unit of
real work, and the achieved throughput (0.09 → 11.5 MiB/s) converges
toward the same ceiling (~11–16 MiB/s) seen in every other sequential-
chunk scenario in this report, as the batch amortizes that fixed cost
over more chunks.

## B5 — request-count / chunk-size effect

Using B1 Case A's 256 MiB median run (4010 unique chunks uploaded,
268,435,456 B, 16.199 s): `executeReplicationPlan` issues exactly one
`fetchSourceChunk` (GET) and one `putSyncChunk` (PUT) per missing unique
chunk, strictly sequentially (confirmed by reading the loop in
`zeros3.go` — see "Is per-chunk HTTP latency the cause?" below) — so
this is 8020 authenticated HTTP round trips in 16.199 s:

- **Average chunk size:** 268,435,456 / 4010 ≈ **66.9 KiB**
- **Requests/sec:** 8020 / 16.199 s ≈ **495 req/s**
- **Estimated average request latency (transaction overhead):** 1 /
  495 ≈ **2.02 ms/request**, on loopback, with negligible real network
  latency and only ~31% of one CPU core's worth of aggregate work
  happening at any given moment (see the CPU-utilization check below) —
  i.e. ~2 ms of largely non-payload-transfer overhead per round trip
  (SigV4 signing/verification, per-chunk SHA-256 digest work, and
  disk I/O on the destination), not 2 ms of "moving 67 KB," which at
  loopback speeds would be sub-microsecond.

## B6 — planning vs. transport

M8G's exposed planner (`replicate -dry-run`) run immediately before the
real transfer, same unchanged source/destination state, 256 MiB
single-object case-A transfer, 3 measured runs:

| Run | Planning | Total | Planning share |
|---|---|---|---|
| 1 | 62 ms | 16.148 s | 0.39% |
| 2 | 66 ms | 16.596 s | 0.40% |
| 3 | 62 ms | 16.670 s | 0.38% |
| **Median** | **62 ms** | **16.596 s** | **0.38%** |

Planning is negligible. Transport is essentially the entire wall clock
(**≥99.6%** of total time, every run). This is the single cleanest
signal in this report: **if planning were the bottleneck, concurrency
would be solving the wrong problem — it plainly isn't here.**

## B7 — loopback environment caveat

Every measurement above runs over `127.0.0.1`. Loopback has effectively
zero real network latency and far more raw bandwidth than any WAN link,
so the ~15 MiB/s ceiling observed everywhere in this report is **not** a
bandwidth limit and **not** a "how fast is the network" number — it is
the throughput of ZeroS3's own sequential per-chunk request/response
cycle running against essentially free network transport. On a real
network with non-trivial RTT, the *same* sequential design would be
worse, not better (see B8's controlled latency experiment, which
directly demonstrates the direction and rough magnitude of that
effect). Nothing in this report should be read as "ZeroS3 does X MiB/s
in production."

## B8 — controlled latency simulation

A tiny stdlib `httputil.ReverseProxy` (benchmark-only, never touching
`zeros3.go`) sits in front of the destination endpoint and adds a fixed
delay to every proxied request before forwarding it; `replicate -to`
simply points at the proxy. 16 MiB object (~250 chunks) so the
experiment stays fast even at 10 ms/request:

| Added delay (per PUT) | Chunks | Elapsed | Throughput | Slowdown vs. 0 ms |
|---|---|---|---|---|
| 0 ms | 263 | 1.165 s | 13.73 MiB/s | 1.0x |
| 1 ms | 247 | 1.348 s | 11.87 MiB/s | 1.16x |
| 5 ms | 246 | 2.536 s | 6.31 MiB/s | 2.18x |
| 10 ms | 253 | 3.889 s | 4.11 MiB/s | **3.34x** |

The added wall time tracks `chunks × delay` almost exactly (e.g. at
10 ms: 253 chunks × 10 ms = 2.53 s predicted added latency vs. 2.72 s
observed added latency — within normal run-to-run chunk-count
variance). This is the direct, measured signature of **zero
pipelining**: each chunk's round trip must fully complete before the
next one starts, so any per-request latency is paid once *per chunk*,
serially, with no overlap whatsoever. A production WAN path with 20–100+
ms RTT would suffer proportionally more than even the 10 ms case shown
here.

## CPU utilization during a large transfer (supporting evidence)

To distinguish "transport is CPU-bound" (parallel HTTP wouldn't help
without also parallelizing hashing) from "transport is wait-bound"
(parallel HTTP would directly help), a 256 MiB case-A replicate was run
once more while sampling `/proc/<pid>/stat` CPU ticks for the source
server, destination server, and `replicate` client processes across the
whole transfer:

```
elapsed=15.98s
src server CPU:       18.8% of one core
dst server CPU:       63.7% of one core
replicate client CPU: 40.5% of one core
total CPU used:      123.0% of one core = 30.8% of the 4 cores available
```

**~69% of this machine's total CPU capacity sat idle for the entire
16-second transfer.** Combined with B6 (negligible planning) and B8
(proven linear latency amplification with no overlap), this rules out
"the single core is pegged doing hashing/crypto and parallel requests
wouldn't help" — there is real, unused capacity on 3 of 4 cores the
whole time, exactly the condition bounded concurrency is designed to
exploit.

## Analysis

**Is sequential chunk transport dominant?** Yes, overwhelmingly. B6
shows planning is 0.4% of total wall time; B1/B2/B4 all converge on the
same ~14–17 MiB/s throughput ceiling regardless of whether the operation
is single-object replication, namespace replication, or peer repair —
consistent with one shared, unparallelized transport primitive being the
universal limiter across every content-moving code path in ZeroS3.

**Which operation suffers most?** B1 Case B and B4 both show the effect
sharpest: throughput *degrades* as the fraction of real missing payload
shrinks (B1b: 15.5 → 4.6 MiB/s from 25% → 95% reuse; B4: 0.09 → 11.5
MiB/s from 1 → 256 bad chunks, in the same direction once read as "small
batch vs. large batch"). Since ZeroS3's whole architectural point is to
minimize what actually needs to move, the *common case* in a mature
deployment (mostly reuse, a little missing) is precisely the case where
fixed per-chunk sequential overhead is proportionally worst.

**Is per-chunk HTTP latency the likely cause?** Yes, directly
demonstrated, not inferred: B8's controlled-delay experiment shows wall
time scaling linearly with `chunks × per-request delay` with no
pipelining, and B5's back-of-envelope shows ~2 ms of overhead per
round trip even on loopback with no artificial delay at all — overhead
inconsistent with "moving 67 KB over loopback" and consistent with fixed
per-request cost (signing, hashing, disk I/O) that concurrent requests
would overlap.

**Does planning matter?** No — B6 puts it at 0.38–0.40% of total time
across three runs. This is not the bottleneck to solve.

**Is disk/hash CPU dominant instead?** No — the CPU-utilization check
shows only ~31% of the machine's 4 cores in use, aggregated across all
three processes, for the full duration of a 256 MiB transfer. There is
substantial idle capacity a bounded worker pool could exploit, both for
overlapping I/O wait and for parallelizing the per-chunk hash/verify
work itself.

**Which worker counts should a future prototype test?** Given a 4-vCPU
environment and a wait-bound (not CPU-saturated) bottleneck, 1 (baseline),
2, 4, 8, and 16 are the natural candidates — expect gains through at
least 4–8, with 16 useful to locate the point where either the
destination server's own request handling or this environment's specific
CPU count becomes the new limiter.

## Decision

**M8H IMPLEMENTATION: STRONG GO**

Every criterion the task set out for a strong case is independently
satisfied by a *measured*, not assumed, result: throughput is low
relative to available CPU and (loopback) network capacity despite
~69% of this machine's CPU sitting idle throughout a representative
transfer (B1/CPU check); many small serialized HTTP round trips
dominate runtime, at roughly 495 requests/sec and ~2 ms overhead per
request even with zero added latency (B5); a controlled latency
experiment shows severe, linear serialized-round-trip amplification —
a modest 10 ms artificial per-request delay produces a measured 3.3x
throughput collapse with no pipelining whatsoever (B8); and payload
transfer dominates planning by roughly 260x (99.6% vs. 0.4%, B6). The
same sequential-transport signature appears identically across single-
object replication, namespace replication, and peer repair, meaning one
shared fix would benefit every content-moving code path in ZeroS3, and
the effect gets *relatively worse*, not better, exactly as CDC/CAS
reuse succeeds and less real payload needs to move (B1b, B4). This is
not a marginal, edge-case-only bottleneck — it is the dominant cost in
every scenario tested that involves genuine missing payload, on a
machine that is not even close to CPU- or bandwidth-saturated.

### Proposed design for a future implementation run (not built in this run)

```
discover / plan  (planReplication / planReplicationNamespace, unchanged)
       |
       v
bounded worker pool (N goroutines over the missing-chunk set)
       |
       v
fetch (source) -> verify length/digest -> upload (destination)
   (exactly today's fetchSourceChunk + putSyncChunk pair, per chunk,
    just N of them in flight at once instead of 1)
       |
       v
aggregate deterministic stats (sum of per-chunk results; order-
independent by construction)
       |
       v
commitSyncObject -- unchanged, single-threaded, only after every
worker has succeeded (preserves the existing atomic-commit contract)
```

- **Shared primitive:** `executeReplicationPlan` (M8A/replicate) and
  `repairFromPeer` (M8B) both do the identical "for each digest: fetch
  from a remote peer, verify, publish locally" loop today, just against
  different peer roles. One bounded-worker-pool helper (e.g.
  `transferChunksConcurrently(fetch func(digest) ([]byte, error),
  publish func(digest, []byte) error, digests []..., workers int)`)
  should back both, rather than two separate concurrent implementations
  drifting apart.
- **Candidate worker counts:** 1 (control), 2, 4, 8, 16 — see "Analysis"
  above.
- **Cancellation:** a `context.Context` cancelled on the first error,
  so in-flight workers stop issuing new requests promptly rather than
  continuing to burn a doomed transfer's worth of bandwidth/CPU.
- **First-error behavior:** today's serial code fails on the first
  chunk (in `plan.unique` order) that errors. A concurrent version
  should preserve *which* error is reported deterministically: collect
  every error that arrives before/at cancellation, then report the one
  whose chunk has the lowest index in `plan.unique` (the plan's existing
  stable order) — not "whichever goroutine happened to lose the race,"
  which would make error messages flaky across runs of the same failure.
- **Memory bound:** already naturally bounded by `workers × max chunk
  size` (262,144 B per CDC v1's frozen max) — trivial even at the
  largest sane worker count.
- **Deterministic stats:** `UploadedBytes`/`UniqueChunksUploaded`/etc.
  are plain sums over the (unordered) completed set — inherently
  order-independent, so no special handling needed beyond the
  first-error determinism above.
- **Retry semantics:** preserve today's *no-retry* behavior exactly
  (one failure aborts the operation) — do not add retry logic as part
  of this change; that is a separate, unscoped decision.
- **Implementation detail to flag up front:** Go's default
  `http.Transport` caps idle connections per host at 2
  (`MaxIdleConnsPerHost`). A naive concurrent implementation reusing the
  existing default-configured client would silently bottleneck at ~2
  concurrent connections to each peer regardless of the configured
  worker count — this needs to be raised (or a per-operation transport
  configured) alongside the worker pool itself, or the benchmark results
  above would not reproduce with concurrency added.
- **Correctness risk — atomicity:** ZeroS3's durability contract
  (`STATUS.md`) already requires every chunk to be durably published
  before commit; gating `commitSyncObject` on *all* workers succeeding
  (not just "most") preserves this unchanged under concurrency.
- **Correctness risk — server-side concurrency:** `zeros3 serve` is an
  ordinary `net/http` server (goroutine-per-request already), so no
  server-side change is anticipated to accept concurrent chunk requests
  safely; this should still be verified explicitly in the next run
  rather than assumed.
