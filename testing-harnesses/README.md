# ZeroS3 testing harnesses

This directory contains ZeroS3's **external black-box validation**.

The root module stays dependency-free. Third-party SDKs and comparison tools
live here, in a separate Go module, and communicate with ZeroS3 only through a
real process, HTTP, CLI, filesystem-observable results, or process lifecycle.

```text
testing-harnesses
        |
        | HTTP / CLI / subprocess
        v
     zeros3 binary
```

Nothing under this module is imported or linked by `zeros3.go`.

## Why two test layers exist

| Layer | Access | Main purpose |
|---|---|---|
| `zeros3_test.go` | white-box | storage invariants, hostile parsing, crash injection, concurrency, race tests |
| `testing-harnesses/` | black-box | real SDK interoperability, process restart/shutdown, application workflows, performance evidence |

Both are necessary.

A storage change can be internally correct but incompatible with a real SDK.
A wire-compatible change can still violate durability or reachability
invariants that are easier to test inside the root package.

## Dependency boundary

The root module:

```text
go.mod
    go 1.27.0
    no require directives
```

The harness module is intentionally different:

```text
testing-harnesses/go.mod
    AWS SDK for Go v2
    minio-go
    transitive client dependencies
```

The dependency boundary is architectural, not cosmetic.

## Portable Core Client Profile

`profile/conformance/` implements ZeroS3 Core Client Profile v1 as a portable
endpoint test.

It can run:

- against a managed ZeroS3 fixture;
- against a supplied endpoint;
- through AWS SDK for Go v2;
- through minio-go adapters;
- with a machine-readable JSON summary.

The profile corresponds to [../S3_COMPAT.md](../S3_COMPAT.md).

Example:

```sh
cd testing-harnesses

go run ./profile/conformance   -endpoint http://127.0.0.1:9000   -access-key K   -secret-key S   -json
```

## Golden vectors

`vectors/` contains fixed interoperability fixtures for independent client
implementations:

- SigV4 canonical requests / strings-to-sign / signatures;
- presigned URL cases;
- representative S3 wire fixtures.

The expected values are not generated by the tests at runtime.

Root tests consume them through the focused vector gate.

These fixtures are especially useful for implementing a ZeroS3-compatible
client in another language.

## Historical result files

`results/` contains recorded development evidence.

they identify the historical run that produced the result.

Treat those files as provenance, not current user documentation.

For current public performance summaries, use

## Build and run one harness

From the repository root:

```sh
go build -o /tmp/zeros3-bin zeros3.go
```

Then:

```sh
cd testing-harnesses

ZEROS3_BIN=/tmp/zeros3-bin go run ./harness/m2
```

Harnesses generally:

- create temporary stores;
- start real ZeroS3 processes on ephemeral ports;
- drive them through an independent client;
- print PASS/FAIL assertions;
- exit nonzero on failure.

Benchmark harnesses may accept `-bin` and emit structured/record lines instead
of using `ZEROS3_BIN`.

## Runner groups

List the current runner groups:

```sh
cd testing-harnesses
go run ./runner -list
```

Common groups:

```sh
go run ./runner -group s3,sync
go run ./runner -group all -bin /tmp/zeros3-bin
go run ./runner -group client,apps
```

The exact group membership is defined by the runner; use `-list` rather than
copying an old milestone command from a result file.

Broad categories include:

| Group | Intent |
|---|---|
| `static` | source/test map checks |
| `s3` | S3 protocol and independent client interoperability |
| `sync` | ZeroS3-native movement/repair/structural workflows |
| `clients` | optional external client/comparison tools |
| `client` | Core Client Profile + physical invariance |
| `apps` | browser-site and checkpoint application scenarios |
| `bench` | performance work; not ordinary correctness validation |

## Optional external programs

Some harnesses use external binaries only when available, for example:

- `rclone`;
- `s3rver`;
- AWS CLI smoke validation;
- `strace` for syscall-count benchmarks.

Do not install an optional program merely to make an unrelated correctness
change pass.

## Benchmark discipline

Performance harnesses are workload/environment-sensitive.

When recording a result:

- identify the source commit(s);
- record object/fixture size;
- identify baseline/current binaries;
- keep same-harness comparisons together;
- record CPU/environment details that materially affect the result;
- distinguish warm/cold page-cache conditions where relevant.

See [../docs/BENCHMARKS.md](../docs/BENCHMARKS.md).

## Adding a harness

Prefer extending an existing harness when the new assertion belongs to an
existing external contract.

Create a new harness when the behavior has a distinct setup/lifecycle or
measurement purpose.

A new harness should:

- drive a real ZeroS3 process;
- generate deterministic fixtures where possible;
- clean up temporary state;
- fail with a nonzero exit;
- avoid depending on private implementation functions;
- document why the black-box layer adds evidence beyond a root unit test.

If it represents a public compatibility claim, update the corresponding public
document in the same change.
