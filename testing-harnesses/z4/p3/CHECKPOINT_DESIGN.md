# Z4-P3 decision: persistent checkpoint (design for P8, not implemented)

## What the measurements say
`BenchmarkP3Open` on the 1,000,000-object fixture (141 packs, 474 MB journal, 5.0 GB store), after the P3 changes, 2.5-2.7 s, 1.35 GB allocated, 13 M allocations. CPU profile (3 opens): journal replay and the namespace it builds (`replayJournalFn` -> `applyRecord`, map inserts, string allocation, the collector scanning the growing namespace) is **about 85%**; reading and indexing pack footers/indexes (`loadPackState`, now concurrent) is **about 10-15%**; segment recovery is negligible.

P1C recommended a *locator* checkpoint. These numbers say it addresses the smaller half: at 1 M objects it could save at most ~0.3 s of 2.6 s. What would pay is a checkpoint of the **namespace** (current objects, retained history, multipart state), with the locator as an optional second section.

## Design (not implemented; P8 candidate)
* `journal/checkpoint-<seq:016x>.zck`, a derived file. The journal stays the only authority; the physical store stays the only authority for chunks. Older binaries ignore unknown names in `journal/`, so the store format level does not move.
* Header: magic, checkpoint version, `store_id` (FORMAT.json), journal sequence `S`, journal byte offset `O` just past frame `S`, CRC32C and sequence of that last frame, creator build id. Body: sorted bucket / key / entry records (varint-packed, strings front-coded), history rows, multipart parts, then an optional locator section (pack ids with size and footer digest, so a changed pack is detected). Trailer: SHA-256 of header + body. Written to `tmp/`, fsynced, renamed, directory fsynced; at most two kept.
* Open: take the newest checkpoint; accept it only if the trailer verifies, `store_id` matches, `O` <= journal size **and the journal frame ending at `O` has sequence `S` and the recorded CRC**; then replay frames after `O` normally (torn-tail rules unchanged). Anything else (missing, truncated, corrupt, wrong store, journal shorter, a frame mismatch, an unknown version) discards it and replays the whole journal: the fallback is the existing code path, always available.
* Never a source of truth: a checkpoint is applied *before* the tail, never after; the journal tail always wins. Reachability, verify, GC and repack do not read it: they keep re-validating the journal (`replayJournalFn`) and the manifests. Pack relocation, segment sealing and repack change the locator, not the namespace; the locator section is validated against pack footers and any disagreement drops that section only.
* Writers: the store owner only, at clean close and every N MiB of journal, off the commit path (a background goroutine that holds `Store.mu` only to copy). Shared openers read, never write.
* Qualification needed before it ships: state-hash equality of checkpoint-open vs full replay after random workloads (put, overwrite, delete, multipart, history prune, bucket create/delete); crash injection at write / fsync / rename / dir fsync / prune; bit-flip and truncation sweeps; stale-checkpoint cases (journal replaced or truncated below `O`, `store_id` mismatch); old and new binaries alternating on one store; a kill -9 loop.

## Economics
Expected open at 1 M objects: read ~100-130 MB sequentially (~0.2-0.4 s) plus the tail; at 10 M roughly 10x that, against ~25 s of replay. Cost: ~1 kLOC plus the qualification above, and a second derived artefact to explain. Verdict for P3: **justified as a separate project for stores of tens of millions of objects, not for today's measured scales** (1 M opens in 2.6 s); not forced into P3.
